# 工程经验教训（E1–E6）

> 本项目（Windows 托盘 + HID++ + Rust + GitHub CI）真实事故的复盘提炼。
> 每条 = 教训 + 真实案例（版本 / commit 级）+ 可执行做法。溯源以仓内锚点（D 编号 / commit / RELEASES.md）为准。

**按用户影响排序的三大事故**：**E1**（开机早期静默 panic，重启后永不识别设备）、**E2**（0 槽位 + 死缓存句柄死锁，托盘永久「?」）、**E3 的 P1**（多设备同睡误判句柄死，触碰零鼠标电池红线）。新手优先吸收这三条。

## E1. Windows 开机时长与 `Instant` 算术陷阱

**教训**：任何 `Instant - Duration` 都必须用 `checked_sub` / `saturating_sub` 保护；语义上溢出时应取「最早合理时刻」而不是崩。「开机自启动」场景必须把「极小 uptime」纳入测试矩阵。GUI 程序一个线程 panic 不一定导致进程退出——**静默部分失效是最危险的故障形态**。

**真实案例**（v0.3.8 真机事故；io_loop 主修复于 v0.3.9 / D-65，同类残留修复于 `02a9fd47`、随 v0.3.13 发布）：

- 现象：系统重启后软件随开机自启，io 线程立即 panic（`overflow when subtracting duration from instant`），但 UI 线程存活——表现为「软件正常启动、托盘图标正常，却永远识别不到设备」。
- 根因与修复（两场修复，勿混）：
  - **主事故（v0.3.8 → v0.3.9）**：io_loop 启动时做 `Instant::now() - Duration::from_secs(60)` 让首次轮询立即到期。Windows 的 `Instant` 基于开机起算的 QPC 计数器，**开机后 60 秒内**该减法下溢直接 panic（真机日志：io 线程在 `io-thread-spawned` 阶段后即死）。该处于 **v0.3.9**（commit `7662575`，D-65 Reconnect 状态机重构：`Option<Instant>` + `saturating_duration_since`）移除。
  - **同类残留（v0.3.13）**：UI 线程 `last_wake_sent = Instant::now() - 10s` 是同一陷阱的残留——uptime < 10s 启动时同样 panic（v0.3.13 Release 正文：「系统开机后约 10 秒内」）。commit `02a9fd47`（实改 `crates/tray/src/main.rs`）把它改为 `Option<Instant>`（None = 从未发送，首个 Raw Input 立即放行），随 v0.3.13 发布。
- 静默放大的原因：release 模式默认 `panic = "unwind"`，线程死亡但进程不退出。本 workspace **有意保持 unwind**（`volttray/Cargo.toml` 注释：PRD 要求 GUI 边界使用 `catch_unwind`，不能开 `panic = "abort"`）——所以「线程级 panic 可见性」必须靠日志 / hook 主动保证，不能指望进程崩溃暴露。

**可执行做法**：

1. 代码审查清单加一条：全仓搜 `Instant::now() -` / `.sub(` 模式，凡出现必须能说明为何不溢出，或改为 `checked_sub` / `saturating_sub` / `Option<Instant>` 语义。
2. 「开机自启」「系统刚启动」类程序，把 uptime ∈ [0, 60s] 区间纳入启动路径测试矩阵。
3. **反直觉现象**：旧版本 panic、新版本不 panic，不构成「新版本已免疫」的证据——可能只是这次运行时 uptime 已足够大、没触发溢出条件。免疫与否必须代码级判定（看算术路径是否还有未保护的减法），不能靠「这次没崩」。

**溯源**：commit `02a9fd47`（UI 线程残留修复）；D-65 状态机重构（io_loop 主修复，`volttray/docs/decisions.md`）；v0.3.13 Release 说明；`volttray/Cargo.toml` release profile 注释。

## E2. 无设备状态的死缓存句柄死锁

**教训**：状态机 / 健康检查必须覆盖「零注册」「全部失败」这类**空集路径**；「重试循环」如果没有失效与重建机制，重试只是原地打转。

**真实案例**（v0.3.10 真机失败，修复于 v0.3.11，决策 D-68）：

- 现象：系统重启后托盘永久显示「?」，30 秒自动重扫永远恢复不了，**唯一出口是手动点「立即刷新」**（`volttray/RELEASES.md` v0.3.11 原文口径）。
- 根因：存活性裁决（`ChannelLiveness`）只在「已注册槽位」的轮询 outcomes 非空时运行；重启后槽位尚未注册 → outcomes 恒为空 → 永不裁决 → 缓存的失效设备句柄永不被废弃 → 每次重扫都复用死句柄。死锁链 = **0 注册槽位 + 死缓存句柄**。
- 修复（D-68，F1+F2+F3）：新增通道级「扫槽连败」裁决 `SlotScanStreak`——连续 3 轮「全部槽位扫描失败且至少一次 I/O 类错误」即强制重开句柄；重开失败整通道作废并触发全量重枚举；无设备态每轮重扫落汇总日志；同版又补上 F5（Raw Input 唤醒事件 + 0 注册槽位时立即强制重枚举，动鼠标即可秒级恢复）。

**可执行做法**：

1. 设计「重试 / 自愈」机制时，先问三个问题：裁决的数据源在空集时还存在吗？失败对象是「本次操作」还是「底层资源（句柄 / 连接）」？底层资源有失效与重建路径吗？
2. 连败计数要**按轮裁决、跨槽位去重**（一轮 7 个槽位全败只记 1 次），否则多设备场景会放大误判（见 E3 的 v0.3.9 打回教训）。
3. 空集 / 全失败路径要有专门的可观测性（本项目：无设备态重扫汇总日志，单会话上限 100 行防爆量）——死锁期间「完全无日志」本身就是设计缺陷。

**溯源**：`volttray/docs/decisions.md` D-68；`volttray/RELEASES.md` v0.3.11；`volttray/crates/app/src/reconnect.rs`。

## E3. HID++ 协议与鼠标休眠的工程现实

**教训**：与外设交互的「失败」要先区分「**设备不应答（正常休眠）**」与「**通道故障（IO 错误）**」，两者处理路径完全不同（纯超时不触发重开，连续 IO 错误才触发）。深度休眠的鼠标不监听射频、不应答查询——**这是物理事实，不是 bug**。

**真实案例与技术要点**：

- **HID++ 1.0 与 2.0 是两套语义**：2.0 全部特性调用使用 20 字节长帧（D-15）；1.0 寄存器读取按 `0x8100|reg` 子地址编码（D-16）；错误帧按协议族分字段解码——同一个错误码 `0x08` 在 1.0 = 设备休眠、在 2.0 = Busy，跨族误判是真机「?」的根因之一（D-17）。
- **槽位扫描**：接收器配对设备按槽位 #1–#6、#255（0xFF）扫描（D-18），扫到空槽位收到 `ERR_INVALID_ARGUMENT` 是**正常应答**，不是错误。
- **项目红线（用户确立）**：任何设计不得以消耗鼠标电池为代价——禁高频轮询、禁对休眠设备主动探测保活；休眠恢复走被动事件（Windows Raw Input）触发（D-33）。
- **轮询成本实测**：一次 HID++ 电量查询约 2 个射频短包，相对鼠标移动上报（125–1000 次/秒）可忽略（60 秒轮询一天 ≈ 活跃使用约 3 秒的无线电耗）。因此轮询间隔应按「**显示新鲜度**」而非「省电」来定（D-66 定档 5/10/30/60/120 分钟，默认 30 分钟，代码常量 `config.rs POLL_TIERS_SECS`）。
- **同族陷阱（v0.3.9 发布前被质检打回的 P1，修复随 v0.3.10 发布）**：通道级超时连击按「次」累计且跨槽位不去重时，同一接收器挂 ≥2 台设备同时休眠，第 2 轮轮询就把正常休眠误判为句柄死亡，导致设备假离线、且此后每 30 秒对休眠槽位主动握手探测——**直接违反零鼠标电池红线**。修复：整轮零应答才记 1 次静默连击，连续 3 轮全静默才判句柄死（D-67）。

**可执行做法**：

1. 失败分类先行：超时 / IO 错误 / 协议错误帧要分通道记录与计数，纯超时类永不触发「资源作废」类动作。
2. 给「省电 / 不打扰」类红线写成可执行的否定句（「对判定休眠的设备零主动查询」），并让每个新方案先过红线再谈功能。
3. 涉及外设耗电的论述用真实数量级估算（包量 × 频次对比设备自身流量），不要凭直觉——本项目就因此把「更短间隔更耗电」的错误文案如实改写（D-66）。

**溯源**：`volttray/docs/decisions.md` D-15/D-16/D-17/D-18/D-33/D-66/D-67/D-68；`volttray/RELEASES.md` v0.3.9/v0.3.10/v0.3.11。

## E4. 诊断导出功能的设计原则

**教训**：**诊断功能必须永不失败**——任何一步失败都要降级而不是整体失败；诊断内容必须覆盖「最需要诊断的状态」（往往就是零设备 / 空状态）；用户提供的诊断要结合物理情境解读。

**真实案例**：

- **v0.3.2 事故**：导出功能自身因目标目录不存在而失败（os error 3）——干净机器上右键「诊断面板/导出」直接报错。修复（v0.3.3，D-40）：抽纯函数 `write_diag_export`，先 `create_dir_all`（覆盖多层嵌套缺失）再写文件，路径 / 权限错误转可读中文提示。
- **空导出教训（v0.3.12，D-69）**：旧导出 = 设备事件流的裸 JSON 数组，在「重启后识别失败」这个最需要诊断的状态下，导出内容只有空数组 `[]`，毫无信息量。重构为对象：`devices`（原事件流）+ `log_tail`（应用日志尾部约 200 行）+ `last_enum`（最近一次枚举快照）+ `exported_at` + `app_version`；**任何子项失败各自降级为空 + reason 字段，导出整体永不报错**，最终序列化失败兜底 `"{}"`。
- **物理解读教训**：一次「空导出」实际是鼠标在休眠、用户没动它，属预期行为；真正的问题是唤醒后恢复慢（后优化为动鼠标约 3.6 秒内恢复，v0.3.11 F5）。诊断数据本身不等于结论。

**可执行做法**：

1. 诊断 / 导出 / 日志类功能按「永不失败」标准写：每个子项独立降级 + 失败原因入结果，不设「整体报错」出口。
2. 设计诊断内容时先想「最坏的现场长什么样」，确保那个现场下导出的东西仍然有信息量（日志尾部、最近一次状态快照、版本号）。
3. 收到用户诊断先重建物理情境（设备是否在休眠 / 用户是否操作过 / 系统是否刚重启），再下结论。

**溯源**：`volttray/docs/decisions.md` D-40/D-69；`volttray/RELEASES.md` v0.3.12；`volttray/crates/app/src/diag_export.rs`。

## E5. CI / GitHub 实战陷阱（沙箱与 API 环境）

**教训**：CI 自动回推会让「main HEAD」与「交付二进制的构建提交」错位，取证口径必须先对齐；GitHub API 权限是分层的，同一 token 不同端点可能部分 403/401；受限网络环境下 git 协议不可用时要会走 REST API 备选通道。

**真实案例与要点**：

- **fmt bot 回推错位**：本仓库 CI（`.github/workflows/ci.yml`）的 fmt 步骤会自动 `cargo fmt` 并把格式化提交回推 main（`style: apply cargo fmt (CI auto-fix)`）。后果：main HEAD 经常比「交付二进制的构建提交」新一个**无 CI 的提交**。取证口径：取最近一个**有 CI 的提交**，用整树 diff（token 多重集比对）证明它与 HEAD 语义等价，并在交付中说明这一错位——否则「HEAD 全绿」是错位的证据。
- **API 权限分层**：同一 token 下 actions runs/jobs 可查，但 logs 端点可能 403、artifact 直连下载可能 401。备选：artifact 可用 nightly.link 免登录镜像下载做哈希比对。
- **git HTTPS 不可用的环境**：部分沙箱 / 受限网络 git HTTPS 完全不可用（TLS/502）。推送代码改走 GitHub contents REST API：`GET /contents/<path>` 取 sha → `PUT /contents/<path>`（base64 内容）；建分支用 `POST /git/refs`。
- **发布规范（本项目确立）**：
  - 版本号升级做**独立 chore 提交**（workspace `Cargo.toml` + `Cargo.lock` 同步），tag 指向该提交；
  - Release 附件哈希**三方一致**：发布者报告、审查者亲算、交付者复验；
  - EXE 内嵌版本资源（FileVersion）也要核对（v0.3.8 起由 `CARGO_PKG_VERSION` 自动派生，杜绝手工同步脱节，D-64）。

**可执行做法**：

1. 引用「CI 全绿」作为证据时，先确认 green run 的 head_sha 与你交付的提交是同一个，或证明语义等价。
2. 取证链路上每个端点失败时先判断是权限分层还是数据不存在，备选通道（镜像下载 / REST API）常备。
3. 发布三件套（tag→commit、哈希、版本资源）逐条独立核验，不互相替代。

**溯源**：`.github/workflows/ci.yml`（fmt auto-fix 段）；`volttray/docs/decisions.md` D-64；`volttray/RELEASES.md` 各版本「未验证项」段。

## E6. Rust / Windows 托盘应用的其他实战经验

**教训**：托盘行为、设备路径、版本号、常量、配置这五类「小事」各有真实踩坑点；每条末尾的「做法」可直接进审查清单。

**托盘图标折叠区（IsPromoted）行为**：Windows 托盘图标存在「提升 / 折叠」状态差异，图标行为在两种状态下不一致是本项目的真实踩坑记录之一（历史记录，当前代码库已无该代码路径）。**做法**：涉及托盘图标的验收要在「图标在折叠区」与「图标在可见区」两种状态下各走一遍。

**双同型号接收器的设备路径去重**（D-19）：两台同型号接收器时，设备路径去重的 path 标签必须包含实例段，否则两台会被合并成一条通道。信道配对按 usage_page `{0xFF00, 0xFF43}`、usage `{1, 2}` 收集短 / 长接口，按 `(pid, 去重 path 标签)` 分组；每请求前双句柄 drain 80 帧；`READ_TIMEOUT = 400ms`。**做法**：多同型号设备场景的去重键必须含实例唯一段；审查时专门检查「两台同型号同时在线」用例。

**版本号管理**：workspace 统一 `version.workspace = true`，升级只动一处（`volttray/Cargo.toml` 的 `workspace.package.version`）+ lock 文件，避免多 crate 版本遗漏。**做法**：版本号升级做独立 chore 提交，tag 指向该提交（见 03 门禁 A1/A2）。

**常量单一来源**：同一组业务常量只允许一处定义。反面教材：轮询档位曾在 tray 侧重复定义 `INTERVALS`，后与 `config::POLL_TIERS_SECS` 漂移，D-62 收敛为唯一来源，设置窗口滑块范围也从常量生成。**做法**：新增常量先全仓搜是否已有定义；审查 diff 时把「同一语义的第二个定义点」当红线项看。

**配置容错哲学**：未知键忽略并产生诊断警告；越界值自动钳制或吸附到最近合法档位，绝不因此拒绝启动；配置加载的每条 warning 逐条写入启动日志（v0.3.8 排查证明：只有数量没有内容的警告计数在真机排查中毫无用处，D-64）。**做法**：配置 / 输入解析按「忽略 + 警告 / 钳制 / 拒绝」三档显式选择策略，警告必须带具体内容落日志。

**溯源**：`volttray/docs/decisions.md` D-19/D-62/D-64；`volttray/Cargo.toml`；`volttray/crates/app/src/config.rs`。

## E16. Windows 专属代码：合并前必须本地交叉验证，别把 CI 当第一道编译器

**教训**：只跑过 Linux 侧 `cargo check/test` 的改动，合 main 后 Windows CI 才第一次编译 `cfg(windows)` 代码——翻车概率高、修复链路长（改代码→推 CI→等跑完→再修）。**Windows 专属代码必须在推送 CI 之前完成本地交叉验证。**

**真实案例**：v0.3.15 合并后首个 CI run 的 clippy 步骤失败，5 个文件报 Windows 专属错误，全部在 Linux 沙箱不可见：

- `windows` crate 0.62.2 没有 `Win32_UI_Dialogs` 模块（正确路径是 `Win32::UI::Controls::Dialogs`）；
- `OPENFILENAMEW` 在 x86_64 目标下无 `Default` 实现（需 `zeroed()` 后逐字段赋值）；
- 测试闭包借用逃逸（改 `to_vec()` 持有）；
- Windows bin target 的 `dead_code`（加 `#[cfg(test)]` 归位）；
- 若干 `collapsible_if` / `let_unit_value`。

研发侧随后用 zig 交叉编译（`x86_64-pc-windows-msvc` target）在 Linux 沙箱本地复现了全部错误、修完再推，第二个 CI run 全绿（详见 `volttray/RELEASES.md` v0.3.15）。后续 T6 修复（D-70/D-71）开工时就把 zig 交叉 check 作为前置步骤执行，同一坑没有再掉第二次。

**可执行做法**：

1. 改动触及 `cfg(windows)` 代码（含 import、API 签名、结构体构造）时，推送 CI 前先在本地做 Windows target 交叉 check：`rustup target add x86_64-pc-windows-msvc` 后用 zig 作 linker 跑 `cargo check --target x86_64-pc-windows-msvc`（沙箱无 MSVC 也能用）；clippy 同样按 Windows target 跑一遍。
2. windows crate 的模块路径与 trait 实现**以所用版本的文档 / 源码为准**，不凭记忆写——crate 小版本之间模块会搬家（上例 `Dialogs` 即如此）。
3. CI 翻车后的修复 commit 里注明「本地交叉验证已过」，让审查者知道这轮不是盲修。

**溯源**：`volttray/RELEASES.md` v0.3.15（CI clippy 翻车与修复记录）；`volttray/docs/decisions.md` D-70（T6 前置交叉验证）。

## E17. 设备身份必须锚定物理设备，而不是某次枚举的通道快照

**教训**：以「本次枚举到的接口 / 通道」做设备身份，任何枚举结果变化（有线↔无线切换、重新枚举、接口增减）都会让**同一台物理设备**裂变出多条身份记录。设备身份必须锚定到物理键（如 unitId / 设备名），枚举产物只能做别名、不能做主键。

**真实案例（T6 根因）**：鼠标有线模式下枚举出 **7 个 USB 接口（MI_00~MI_06）**，每个接口各注册一条通道 → 同一台物理鼠标被注册 7 次，托盘与台账里出现 7 个重复条目。修复设计（D-70）：

- 引入 **PhysicalKey**（优先 unitId、退化用设备名）作为身份主键；
- proven_matches 记录已证实的「通道 ↔ 物理键」对应，重枚举时按 physical_key 去重；
- rebind-on-match：通道重建但物理键命中时直接换绑而非新建；
- 别名槽位（alias slots）吸收枚举抖动。

红队复审又挖出 **P1「晋级验明」**：别名槽位里冻结的 unitId 永久有效，若设备在别名存活期内经 RF 重新配对（物理设备换了、名字没变），晋级路径会把鼠标 A 的台账绑到鼠标 B 的端点上、B 被永久抑制。必修项（D-71 P1-1）：**晋级前重新验明 unitId**，验不过不晋级。配套必修：统一移除路径顺序（P2-1）、修正空集恒真断言（P2-2）；瞬时 unitId 读取失败、rebind 返回值忽略两条按已知限制记录（P2-3/P2-4）。裁决原话：「**数据完整性风险不用进度换**。」修复合并于 main（T6，22 项新增单测）。

**可执行做法**：

1. 设计任何「记住这台设备」的机制时，先问：这个键在重枚举 / 换连接方式 / 换接收器后还稳定吗？不稳定就不能做主键。
2. 身份晋级（试探身份 → 确认身份）路径上，晋级动作前必须**当下重新验明**，不采信缓存身份——缓存只能缩小验明范围，不能替代验明。
3. 审查同类代码时专项想攻击面：「如果同名设备被掉包 / 重配对，哪条路径会把 A 的数据记到 B 头上？」

**溯源**：`volttray/docs/decisions.md` D-70（根因与 PhysicalKey 设计）、D-71（红蓝必修 P1-1 晋级验明）；合并提交 `700ccf80`（main）。

**适用边界**：物理键本身也可能读不到（设备休眠、瞬时 IO 失败）——此时按「身份不明」处理、保持试探态，不可退化回通道快照当身份（D-71 P2-3 按已知限制记录）。

## E18. 托盘应用性能审查：先定性每个周期「唤醒几次、查几次、画几次」，再谈优化

**教训**：常驻托盘程序的性能问题不靠直觉找，要把**稳态下的周期行为**逐一摆上台面：每个轮询周期唤醒几次、发起几次设备查询、分配多少内存、定时器空转多少次。优化目标不是「快」，是「**不该动的时候零动作**」。

**真实案例（v0.3.15 性能审查与优化）**：审查先给两处旧认知定性纠偏，再抓出两个 P1：

- **30 秒槽位扫描定性**：槽位扫描嵌在枚举循环内，30 秒门限只在**外层循环每次迭代**时检查——空闲时一个轮询周期最多扫一次（默认 1800 秒一档下即 30 分钟一次），并非「每 30 秒例行枚举」；设备活跃期才可能 ≤30 秒一次。文档中「30s routine enumeration」的表述为误记，随 v0.3.15 修正。该行为后经对照实验正式定性为**设计行为**并关闭存疑项：扫描暂停 15 分钟期间鼠标侧事件为 0，恢复前后为 42~75 事件/分钟——扫描不打扰设备。
- **P1-1 唤醒信号绕过轮询档**：某唤醒路径绕过轮询节流，以约 0.5Hz 持续发起查询——相对 1800 秒档是约 900 倍放大的「查询风暴」。修复：唤醒路径并入节流。
- **P1-2 图标缓存 824 帧预渲染**：全部电量档位 × 状态的图标一次性预渲染常驻内存（16px 约 0.8MB、48px 约 7.4MB）。修复：改懒加载 + LRU（32 帧上限），稳态占用降到数百 KB。
- **P2 级**：bootlog 原只在启动时轮转 → 改运行期超 1MB 即轮转；闪烁定时器改按需启停；休眠改按需。

**可执行做法**：

1. 审查常驻程序先做「稳态账」：默认配置、无用户操作时，一分钟内发生多少次设备 I/O、多少次定时器回调、多少常驻分配？每一项都要能说出「为什么必须」。
2. 对任何周期性行为，先读代码确认门限在**哪一层循环**生效——「门限值」和「实际频率」之间隔着循环结构，文档口径也要按实际结构写。
3. 优化有效性用数字收口：优化前后各给一组可复核的量（查询频率倍数、内存量级），不接受「应该更省了」。

**溯源**：`volttray/RELEASES.md` v0.3.15（P1-1/P1-2/P2 各项修复与口径修正）。

## E19. 平台移植评估：先分层判定「能不能」，再算「值不值」，硬门禁放在第一天

**教训**：「能不能支持旧系统」不能凭感觉答。把依赖拆层——语言工具链基线、系统 API、运行时组件、协议本身——逐层判定卡在哪；工作量估算配一个**第一天就兑现的硬门禁**，避免投入数日后才撞墙。

**真实案例（Win7 移植评估，结论：不做）**：四层判定的实际结果——

- **Rust 工具链**：1.78 起官方基线即 Windows 10（本项目锁 1.90.0）——卡在第一层；
- **系统 API**：`GetDpiForWindow` / `SetProcessDpiAwarenessContext` 为 Win10 专有；
- **WinRT toast**：Win8+；
- **HID++ 电量读取本身**：与 OS 版本无关——协议层从来不是障碍。

若硬做的估算约 3~4 人日（编译开关隔离 DPI/toast 路径），但硬门禁是：**第 1 天先在真实 Win7 虚拟机上验证最小托盘程序能跑**，跑不过立即止损。被否掉的路线是「冻结旧版 Rust 分支」——留下永久维护税。结论连同「系统要求：Windows 10/11 x64」写进根 README，防止同一问题反复被问。

**可执行做法**：

1. 移植评估按「工具链 → 系统 API → 运行时 → 业务协议」四层逐层出结论，每层给「支持 / 不支持 / 需绕过」与依据（官方 MSRV、API 文档的最低系统版本）。
2. 给「做」的方案必配第一天硬门禁（最小可行程序在目标平台真机 / 真虚拟机跑通），不过即止损。
3. 「不做」也是正式结论：写清四层依据 + 被否路线的维护成本，落到公开文档（README 系统要求段），一次关闭、不再重议。

**溯源**：根 `README.md`「系统要求」段（Windows 10/11 x64 结论的落点）。

**适用边界**：评估结论随工具链与依赖版本漂移，引用时标注评估时点；本项目评估时点为 v0.3.15 前后。

## E20. 本地文件有界 & 绝不自动删除用户文件

**教训**：常驻程序的本地文件（日志、导出、缓存）必须**全部有界**：单文件有上限或轮转、文件数量不无限繁殖。更重要的红线：**绝不自动删除用户文件**——程序自己写的导出文件，一旦交给用户（另存到用户自选位置）就是用户的，软件无权回收。

**真实案例**：

- **日志运行期轮转（v0.3.15）**：bootlog 原仅启动时轮转，长跑场景单文件可无限增长；改为运行期超过 1MB 即轮转，占用有界。
- **诊断导出改「另存为」（v0.3.15）**：导出从「程序写固定目录」改为用户自选位置，文件名带本地时间戳（形如 `LogiVoltTray-diag-export-YYYYMMDD-HHMMSS-mmm.json`）。
- **用户红线否决自动清理**：曾有方案让导出目录「自动只保留最近 10 份历史文件」，被用户明确否决——「自己选位置会自己管理，删除会影响管理」。该红线随后全链路落实（见 [02 E24](02-collaboration-playbook.md#e24-用户红线全链路传导写进每个环节的验收标准)）。

**可执行做法**：

1. 盘点程序写盘的每个角落（日志 / 导出 / 缓存 / 注册表 / 内存驻留），逐个回答「上界是什么」；答不上来的就是要修的洞。设计文档中把「单文件有界或轮转、文件不许无限繁殖、绝不删除用户文件」写成显式约束。
2. 区分「程序的自留地」（程序全权管理的临时文件，可自行轮转清理）与「交给用户的文件」（导出、报告）——后者只增不删，清理权永远归用户。
3. 审查 diff 时对「delete / remove / 清理 / 保留最近 N 份」字样做专项检索，命中用户文件路径即打回。

**溯源**：`volttray/RELEASES.md` v0.3.15（日志运行期轮转、诊断导出另存为）。
