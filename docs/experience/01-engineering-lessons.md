# 工程经验教训

> 本项目（Windows 托盘 + HID++ + Rust + GitHub CI）真实事故的复盘提炼。
> 每条 = 教训 + 真实案例（版本 / commit 级）+ 可执行做法。溯源以仓内锚点（D 编号 / commit / RELEASES.md）为准。
> 条目覆盖范围的单一来源为 [README 索引](README.md#e-编号总索引)。

**按用户影响排序的三大事故**：**E1**（开机早期静默 panic，重启后永不识别设备）、**E2**（0 槽位 + 死缓存句柄死锁，托盘永久「?」）、**E3 的 P1**（多设备同睡误判句柄死，触碰零鼠标电池红线）。新手优先吸收这三条。

## E1. Windows 开机时长与 `Instant` 算术陷阱

**教训**：任何 `Instant - Duration` 都必须用 `checked_sub` / `saturating_sub` 保护；语义上溢出时应取「最早合理时刻」而不是崩。「开机自启动」场景必须把「极小 uptime」纳入测试矩阵。GUI 程序一个线程 panic 不一定导致进程退出——**静默部分失效是最危险的故障形态**。

**真实案例**（v0.3.8 真机事故；io_loop 主修复于 v0.3.9 / D-65，同类残留修复于 `02a9fd47`、随 v0.3.13 发布）：

- 现象：系统重启后软件随开机自启，io 线程立即 panic（`overflow when subtracting duration from instant`），但 UI 线程存活——表现为「软件正常启动、托盘图标正常，却永远识别不到设备」。
- 根因与修复（两场修复，勿混）：
  - **主事故（v0.3.8 → v0.3.9）**：io_loop 启动时做 `Instant::now() - Duration::from_secs(60)` 让首次轮询立即到期。Windows 的 `Instant` 基于开机起算的 QPC 计数器，**开机后 60 秒内**该减法下溢直接 panic（真机日志：io 线程在 `io-thread-spawned` 阶段后即死）。该处于 **v0.3.9**（commit `7662575`，D-65 Reconnect 状态机重构：`Option<Instant>` + `saturating_duration_since`）移除。
  - **同类残留（v0.3.13）**：UI 线程 `last_wake_sent = Instant::now() - 10s` 是同一陷阱的残留——uptime < 10s 启动时同样 panic（v0.3.13 Release 正文：「系统开机后约 10 秒内」）。commit `02a9fd47`（实改 `crates/tray/src/main.rs`）把它改为 `Option<Instant>`（None = 从未发送，首个 Raw Input 立即放行），随 v0.3.13 发布。
- 静默放大的原因：release 模式默认 `panic = "unwind"`，线程死亡但进程不退出。本 workspace **有意保持 unwind**（`volttray/Cargo.toml` 注释：PRD 要求 GUI 边界使用 `catch_unwind`，不能开 `panic = "abort"`）——所以「线程级 panic 可见性」必须靠日志 / hook 主动保证，不能指望进程崩溃暴露。

**可执行做法**：

1. 代码审查清单加一条：全仓搜 `Instant::now() -` / `.sub(` 模式，凡出现必须能说明为何不溢出，或改为 `checked_sub` / `saturating_sub` / `Option<Instant>` 语义。
2. 「开机自启」「系统刚启动」类程序，把 uptime ∈ [0, 60s] 区间纳入启动路径测试矩阵。
3. **反直觉现象**：旧版本 panic、新版本不 panic，不构成「新版本已免疫」的证据——可能只是这次运行时 uptime 已足够大、没触发溢出条件。免疫与否必须代码级判定（看算术路径是否还有未保护的减法），不能靠「这次没崩」。

**溯源**：commit `02a9fd47`（UI 线程残留修复）；D-65 状态机重构（io_loop 主修复，`volttray/docs/decisions.md`）；v0.3.13 Release 说明；`volttray/Cargo.toml` release profile 注释。

## E2. 无设备状态的死缓存句柄死锁

**教训**：状态机 / 健康检查必须覆盖「零注册」「全部失败」这类**空集路径**；「重试循环」如果没有失效与重建机制，重试只是原地打转。

**真实案例**（v0.3.10 真机失败，修复于 v0.3.11，决策 D-68）：

- 现象：系统重启后托盘永久显示「?」，30 秒自动重扫永远恢复不了，**唯一出口是手动点「立即刷新」**（`volttray/RELEASES.md` v0.3.11 原文口径）。
- 根因：存活性裁决（`ChannelLiveness`）只在「已注册槽位」的轮询 outcomes 非空时运行；重启后槽位尚未注册 → outcomes 恒为空 → 永不裁决 → 缓存的失效设备句柄永不被废弃 → 每次重扫都复用死句柄。死锁链 = **0 注册槽位 + 死缓存句柄**。
- 修复（D-68，F1+F2+F3）：新增通道级「扫槽连败」裁决 `SlotScanStreak`——连续 3 轮「全部槽位扫描失败且至少一次 I/O 类错误」即强制重开句柄；重开失败整通道作废并触发全量重枚举；无设备态每轮重扫落汇总日志；同版又补上 F5（Raw Input 唤醒事件 + 0 注册槽位时立即强制重枚举，动鼠标即可秒级恢复）。

**可执行做法**：

1. 设计「重试 / 自愈」机制时，先问三个问题：裁决的数据源在空集时还存在吗？失败对象是「本次操作」还是「底层资源（句柄 / 连接）」？底层资源有失效与重建路径吗？
2. 连败计数要**按轮裁决、跨槽位去重**（一轮 7 个槽位全败只记 1 次），否则多设备场景会放大误判（见 E3 的 v0.3.9 打回教训）。
3. 空集 / 全失败路径要有专门的可观测性（本项目：无设备态重扫汇总日志，单会话上限 100 行防爆量）——死锁期间「完全无日志」本身就是设计缺陷。

**溯源**：`volttray/docs/decisions.md` D-68；`volttray/RELEASES.md` v0.3.11；`volttray/crates/app/src/reconnect.rs`。

## E3. HID++ 协议与鼠标休眠的工程现实

**教训**：与外设交互的「失败」要先区分「**设备不应答（正常休眠）**」与「**通道故障（IO 错误）**」，两者处理路径完全不同（纯超时不触发重开，连续 IO 错误才触发）。深度休眠的鼠标不监听射频、不应答查询——**这是物理事实，不是 bug**。

**真实案例与技术要点**：

- **HID++ 1.0 与 2.0 是两套语义**：2.0 全部特性调用使用 20 字节长帧（D-15）；1.0 寄存器读取按 `0x8100|reg` 子地址编码（D-16）；错误帧按协议族分字段解码——同一个错误码 `0x08` 在 1.0 = 设备休眠、在 2.0 = Busy，跨族误判是真机「?」的根因之一（D-17）。
- **槽位扫描**：接收器配对设备按槽位 #1–#6、#255（0xFF）扫描（D-18），扫到空槽位收到 `ERR_INVALID_ARGUMENT` 是**正常应答**，不是错误。
- **项目红线（用户确立）**：任何设计不得以消耗鼠标电池为代价——禁高频轮询、禁对休眠设备主动探测保活；休眠恢复走被动事件（Windows Raw Input）触发（D-33）。
- **轮询成本实测**：一次 HID++ 电量查询约 2 个射频短包，相对鼠标移动上报（125–1000 次/秒）可忽略（60 秒轮询一天 ≈ 活跃使用约 3 秒的无线电耗）。因此轮询间隔应按「**显示新鲜度**」而非「省电」来定（D-66 定档 5/10/30/60/120 分钟，默认 30 分钟，代码常量 `config.rs POLL_TIERS_SECS`）。
- **同族陷阱（v0.3.9 发布前被质检打回的 P1，修复随 v0.3.10 发布）**：通道级超时连击按「次」累计且跨槽位不去重时，同一接收器挂 ≥2 台设备同时休眠，第 2 轮轮询就把正常休眠误判为句柄死亡，导致设备假离线、且此后每 30 秒对休眠槽位主动握手探测——**直接违反零鼠标电池红线**。修复：整轮零应答才记 1 次静默连击，连续 3 轮全静默才判句柄死（D-67）。

**可执行做法**：

1. 失败分类先行：超时 / IO 错误 / 协议错误帧要分通道记录与计数，纯超时类永不触发「资源作废」类动作。
2. 给「省电 / 不打扰」类红线写成可执行的否定句（「对判定休眠的设备零主动查询」），并让每个新方案先过红线再谈功能。
3. 涉及外设耗电的论述用真实数量级估算（包量 × 频次对比设备自身流量），不要凭直觉——本项目就因此把「更短间隔更耗电」的错误文案如实改写（D-66）。

**溯源**：`volttray/docs/decisions.md` D-15/D-16/D-17/D-18/D-33/D-66/D-67/D-68；`volttray/RELEASES.md` v0.3.9/v0.3.10/v0.3.11。

## E4. 诊断导出功能的设计原则

**教训**：**诊断功能必须永不失败**——任何一步失败都要降级而不是整体失败；诊断内容必须覆盖「最需要诊断的状态」（往往就是零设备 / 空状态）；用户提供的诊断要结合物理情境解读。

**真实案例**：

- **v0.3.2 事故**：导出功能自身因目标目录不存在而失败（os error 3）——干净机器上右键「诊断面板/导出」直接报错。修复（v0.3.3，D-40）：抽纯函数 `write_diag_export`，先 `create_dir_all`（覆盖多层嵌套缺失）再写文件，路径 / 权限错误转可读中文提示。
- **空导出教训（v0.3.12，D-69）**：旧导出 = 设备事件流的裸 JSON 数组，在「重启后识别失败」这个最需要诊断的状态下，导出内容只有空数组 `[]`，毫无信息量。重构为对象：`devices`（原事件流）+ `log_tail`（应用日志尾部约 200 行）+ `last_enum`（最近一次枚举快照）+ `exported_at` + `app_version`；**任何子项失败各自降级为空 + reason 字段，导出整体永不报错**，最终序列化失败兜底 `"{}"`。
- **物理解读教训**：一次「空导出」实际是鼠标在休眠、用户没动它，属预期行为；真正的问题是唤醒后恢复慢（后优化为动鼠标约 3.6 秒内恢复，v0.3.11 F5）。诊断数据本身不等于结论。

> 注（2026-10-23）：上条「动鼠标约 3.6 秒内恢复」为实测经验值，仓内无测量记录，无法经仓库独立复核。

**可执行做法**：

1. 诊断 / 导出 / 日志类功能按「永不失败」标准写：每个子项独立降级 + 失败原因入结果，不设「整体报错」出口。
2. 设计诊断内容时先想「最坏的现场长什么样」，确保那个现场下导出的东西仍然有信息量（日志尾部、最近一次状态快照、版本号）。
3. 收到用户诊断先重建物理情境（设备是否在休眠 / 用户是否操作过 / 系统是否刚重启），再下结论。

**溯源**：`volttray/docs/decisions.md` D-40/D-69；`volttray/RELEASES.md` v0.3.12；`volttray/crates/app/src/diag_export.rs`。

## E5. CI / GitHub 实战陷阱（沙箱与 API 环境）

**教训**：CI 自动回推会让「main HEAD」与「交付二进制的构建提交」错位，取证口径必须先对齐；GitHub API 权限是分层的，同一 token 不同端点可能部分 403/401；受限网络环境下 git 协议不可用时要会走 REST API 备选通道。

**真实案例与要点**：

- **fmt bot 回推错位**：本仓库 CI（`.github/workflows/ci.yml`）的 fmt 步骤会自动 `cargo fmt` 并把格式化提交回推 main（`style: apply cargo fmt (CI auto-fix)`）。后果：main HEAD 经常比「交付二进制的构建提交」新一个**无 CI 的提交**。取证口径：取最近一个**有 CI 的提交**，用整树 diff（token 多重集比对）证明它与 HEAD 语义等价，并在交付中说明这一错位——否则「HEAD 全绿」是错位的证据。
> 注（2026-10-19）：本要点所述 fmt 自动回推机制已自 v0.3.17 废除（改为 `cargo fmt --check`、不一致即失败由作者本地修复，见 E31 / D-79）。本要点保留为历史案例；「引用 CI 全绿先对齐 head_sha」的取证教训仍然有效。
- **API 权限分层**：同一 token 下 actions runs/jobs 可查，但 logs 端点可能 403、artifact 直连下载可能 401。备选：artifact 可用 nightly.link 免登录镜像下载做哈希比对。
- **git HTTPS 不可用的环境**：部分沙箱 / 受限网络 git HTTPS 完全不可用（TLS/502）。推送代码改走 GitHub contents REST API：`GET /contents/<path>` 取 sha → `PUT /contents/<path>`（base64 内容）；建分支用 `POST /git/refs`。
- **发布规范（本项目确立）**：
  - 版本号升级做**独立 chore 提交**（workspace `Cargo.toml` + `Cargo.lock` 同步），tag 指向该提交；
  - Release 附件哈希**三方一致**：发布者报告、审查者亲算、交付者复验；
  - EXE 内嵌版本资源（FileVersion）也要核对（v0.3.8 起由 `CARGO_PKG_VERSION` 自动派生，杜绝手工同步脱节，D-64）。

> 注（2026-10-23）：上组发布规范中「tag 指向版本号 chore 提交」为规范口径，实际执行存在偏差实例——**v0.3.19 的 tag 实际指向 clippy fix-forward 提交 `48676bf138c9`**，而非版本号 chore 提交 `1dd9856492f4`（实际链序：`e974c736aa` → `1dd9856492f4` chore(release): v0.3.19 → `e702bdec4b` rustfmt fix-forward → `48676bf138c9` clippy fix-forward，tag 打在链尾，与 E32 所记 v0.3.19 两次 fix-forward 一致）。tag 一经发布不可动，此处如实登记指向偏差；对 v0.3.19 做二进制 / 提交溯源时，以 tag 实际指向的 `48676bf138c9` 为准。

**可执行做法**：

1. 引用「CI 全绿」作为证据时，先确认 green run 的 head_sha 与你交付的提交是同一个，或证明语义等价。
2. 取证链路上每个端点失败时先判断是权限分层还是数据不存在，备选通道（镜像下载 / REST API）常备。
3. 发布三件套（tag→commit、哈希、版本资源）逐条独立核验，不互相替代。

**溯源**：`.github/workflows/ci.yml`（fmt auto-fix 段）；`volttray/docs/decisions.md` D-64；`volttray/RELEASES.md` 各版本「未验证项」段。

## E6. Rust / Windows 托盘应用的其他实战经验

**教训**：托盘行为、设备路径、版本号、常量、配置这五类「小事」各有真实踩坑点；每条末尾的「做法」可直接进审查清单。

**托盘图标折叠区（IsPromoted）行为**：Windows 托盘图标存在「提升 / 折叠」状态差异，图标行为在两种状态下不一致是本项目的真实踩坑记录之一（历史记录，当前代码库已无该代码路径）。**做法**：涉及托盘图标的验收要在「图标在折叠区」与「图标在可见区」两种状态下各走一遍。

**双同型号接收器的设备路径去重**（D-19）：两台同型号接收器时，设备路径去重的 path 标签必须包含实例段，否则两台会被合并成一条通道。信道配对按 usage_page `{0xFF00, 0xFF43}`、usage `{1, 2}` 收集短 / 长接口，按 `(pid, 去重 path 标签)` 分组；每请求前双句柄 drain 80 帧；`READ_TIMEOUT = 400ms`。**做法**：多同型号设备场景的去重键必须含实例唯一段；审查时专门检查「两台同型号同时在线」用例。

**版本号管理**：workspace 统一 `version.workspace = true`，升级只动一处（`volttray/Cargo.toml` 的 `workspace.package.version`）+ lock 文件，避免多 crate 版本遗漏。**做法**：版本号升级做独立 chore 提交，tag 指向该提交（见 03 门禁 A1/A2）。

**常量单一来源**：同一组业务常量只允许一处定义。反面教材：轮询档位曾在 tray 侧重复定义 `INTERVALS`，后与 `config::POLL_TIERS_SECS` 漂移，D-62 收敛为唯一来源，设置窗口滑块范围也从常量生成。**做法**：新增常量先全仓搜是否已有定义；审查 diff 时把「同一语义的第二个定义点」当红线项看。

**配置容错哲学**：未知键忽略并产生诊断警告；越界值自动钳制或吸附到最近合法档位，绝不因此拒绝启动；配置加载的每条 warning 逐条写入启动日志（v0.3.8 排查证明：只有数量没有内容的警告计数在真机排查中毫无用处，D-64）。**做法**：配置 / 输入解析按「忽略 + 警告 / 钳制 / 拒绝」三档显式选择策略，警告必须带具体内容落日志。

**溯源**：`volttray/docs/decisions.md` D-19/D-62/D-64；`volttray/Cargo.toml`；`volttray/crates/app/src/config.rs`。

## E16. Windows 专属代码：合并前必须本地交叉验证，别把 CI 当第一道编译器

**教训**：只跑过 Linux 侧 `cargo check/test` 的改动，合 main 后 Windows CI 才第一次编译 `cfg(windows)` 代码——翻车概率高、修复链路长（改代码→推 CI→等跑完→再修）。**Windows 专属代码必须在推送 CI 之前完成本地交叉验证。**

**真实案例**：v0.3.15 合并后首个 CI run 的 clippy 步骤失败，5 个文件报 Windows 专属错误，全部在 Linux 沙箱不可见：

- `windows` crate 0.62.2 没有 `Win32_UI_Dialogs` 模块（正确路径是 `Win32::UI::Controls::Dialogs`）；
- `OPENFILENAMEW` 在 x86_64 目标下无 `Default` 实现（需 `zeroed()` 后逐字段赋值）；
- 测试闭包借用逃逸（改 `to_vec()` 持有）；
- Windows bin target 的 `dead_code`（加 `#[cfg(test)]` 归位）；
- 若干 `collapsible_if` / `let_unit_value`。

研发侧随后用 zig 交叉编译（`x86_64-pc-windows-msvc` target）在 Linux 沙箱本地复现了全部错误、修完再推，第二个 CI run 全绿（详见 `volttray/RELEASES.md` v0.3.15）。后续 T6 修复（D-70/D-71）开工时就把 zig 交叉 check 作为前置步骤执行，同一坑没有再掉第二次。

**可执行做法**：

1. 改动触及 `cfg(windows)` 代码（含 import、API 签名、结构体构造）时，推送 CI 前先在本地做 Windows target 交叉 check：`rustup target add x86_64-pc-windows-msvc` 后用 zig 作 linker 跑 `cargo check --target x86_64-pc-windows-msvc`（沙箱无 MSVC 也能用）；clippy 同样按 Windows target 跑一遍。
2. windows crate 的模块路径与 trait 实现**以所用版本的文档 / 源码为准**，不凭记忆写——crate 小版本之间模块会搬家（上例 `Dialogs` 即如此）。
3. CI 翻车后的修复 commit 里注明「本地交叉验证已过」，让审查者知道这轮不是盲修。

**溯源**：`volttray/RELEASES.md` v0.3.15（CI clippy 翻车与修复记录）；`volttray/docs/decisions.md` D-70（T6 前置交叉验证）。

## E17. 设备身份必须锚定物理设备，而不是某次枚举的通道快照

**教训**：以「本次枚举到的接口 / 通道」做设备身份，任何枚举结果变化（有线↔无线切换、重新枚举、接口增减）都会让**同一台物理设备**裂变出多条身份记录。设备身份必须锚定到物理键（如 unitId / 设备名），枚举产物只能做别名、不能做主键。

**真实案例（T6 根因）**：鼠标有线模式下枚举出 **7 个 USB 接口（MI_00~MI_06）**，每个接口各注册一条通道 → 同一台物理鼠标被注册 7 次，托盘与台账里出现 7 个重复条目。修复设计（D-70）：

- 引入 **PhysicalKey**（优先 unitId、退化用设备名）作为身份主键；
- proven_matches 记录已证实的「通道 ↔ 物理键」对应，重枚举时按 physical_key 去重；
- rebind-on-match：通道重建但物理键命中时直接换绑而非新建；
- 别名槽位（alias slots）吸收枚举抖动。

红队复审又挖出 **P1「晋级验明」**：别名槽位里冻结的 unitId 永久有效，若设备在别名存活期内经 RF 重新配对（物理设备换了、名字没变），晋级路径会把鼠标 A 的台账绑到鼠标 B 的端点上、B 被永久抑制。必修项（D-71 P1-1）：**晋级前重新验明 unitId**，验不过不晋级。配套必修：统一移除路径顺序（P2-1）、修正空集恒真断言（P2-2）；瞬时 unitId 读取失败、rebind 返回值忽略两条按已知限制记录（P2-3/P2-4）。裁决原话：「**数据完整性风险不用进度换**。」修复合并于 main（T6，净增 19 项单测——按「v0.3.15 tag → 合并提交 `700ccf80`」测试名 diff 静态计数口径；交付时自报的「22 例」与实测不一致，以实测为准）。

**可执行做法**：

1. 设计任何「记住这台设备」的机制时，先问：这个键在重枚举 / 换连接方式 / 换接收器后还稳定吗？不稳定就不能做主键。
2. 身份晋级（试探身份 → 确认身份）路径上，晋级动作前必须**当下重新验明**，不采信缓存身份——缓存只能缩小验明范围，不能替代验明。
3. 审查同类代码时专项想攻击面：「如果同名设备被掉包 / 重配对，哪条路径会把 A 的数据记到 B 头上？」

**溯源**：`volttray/docs/decisions.md` D-70（根因与 PhysicalKey 设计）、D-71（红蓝必修 P1-1 晋级验明）；合并提交 `700ccf80`（main）。

**发布状态**：修复**已随 v0.3.16 发布**（与 [04 §7 第三步](04-onboarding.md) 口径一致：修复提交 `5e265e26b0b`、`700ccf80bd0` 在 v0.3.15…v0.3.16 提交区间内）——对 ≤v0.3.15 的用户可建议升级至 ≥v0.3.16。

**适用边界**：物理键本身也可能读不到（设备休眠、瞬时 IO 失败）——此时按「身份不明」处理、保持试探态，不可退化回通道快照当身份（D-71 P2-3 按已知限制记录）。

## E18. 托盘应用性能审查：先定性每个周期「唤醒几次、查几次、画几次」，再谈优化

**教训**：常驻托盘程序的性能问题不靠直觉找，要把**稳态下的周期行为**逐一摆上台面：每个轮询周期唤醒几次、发起几次设备查询、分配多少内存、定时器空转多少次。优化目标不是「快」，是「**不该动的时候零动作**」。

**真实案例（v0.3.15 性能审查与优化）**：审查先给两处旧认知定性纠偏，再抓出两个 P1：

- **30 秒槽位扫描定性**：槽位扫描嵌在枚举循环内，30 秒门限只在**外层循环每次迭代**时检查——空闲时一个轮询周期最多扫一次（默认 1800 秒一档下即 30 分钟一次），并非「每 30 秒例行枚举」；设备活跃期才可能 ≤30 秒一次。文档中「30s routine enumeration」的表述为误记，随 v0.3.15 修正。该行为后经对照实验正式定性为**设计行为**并关闭存疑项：扫描暂停 15 分钟期间鼠标侧事件为 0，恢复前后为 42~75 事件/分钟——扫描不打扰设备。
- **P1-1 唤醒信号绕过轮询档**：某唤醒路径绕过轮询节流，以约 0.5Hz 持续发起查询——相对 1800 秒档是约 900 倍放大的「查询风暴」。修复：唤醒路径并入节流。
- **P1-2 图标缓存 824 帧预渲染**：全部电量档位 × 状态的图标一次性预渲染常驻内存（16px 约 0.8MB、48px 约 7.4MB）。修复：改懒加载 + LRU（32 帧上限），稳态占用降到数百 KB。
- **P2 级**：bootlog 原只在启动时轮转 → 改运行期超 1MB 即轮转；闪烁定时器改按需启停；休眠改按需。

> 注（2026-10-23）：本条案例中的实验与度量数字——对照实验读数（扫描暂停 15 分钟、鼠标侧事件为 0、恢复前后 42~75 事件/分钟）与预渲染基线度量（824 帧、16px 约 0.8MB / 48px 约 7.4MB）——数据来自仓外实验记录，未入仓，无法经仓库独立复核；「上限 32 帧、稳态数百 KB」与各项修复行为可对 `volttray/RELEASES.md` v0.3.15 溯源。

**可执行做法**：

1. 审查常驻程序先做「稳态账」：默认配置、无用户操作时，一分钟内发生多少次设备 I/O、多少次定时器回调、多少常驻分配？每一项都要能说出「为什么必须」。
2. 对任何周期性行为，先读代码确认门限在**哪一层循环**生效——「门限值」和「实际频率」之间隔着循环结构，文档口径也要按实际结构写。
3. 优化有效性用数字收口：优化前后各给一组可复核的量（查询频率倍数、内存量级），不接受「应该更省了」。

**溯源**：`volttray/RELEASES.md` v0.3.15（P1-1/P1-2/P2 各项修复与口径修正）。

## E19. 平台移植评估：先分层判定「能不能」，再算「值不值」，硬门禁放在第一天

**教训**：「能不能支持旧系统」不能凭感觉答。把依赖拆层——语言工具链基线、系统 API、运行时组件、协议本身——逐层判定卡在哪；工作量估算配一个**第一天就兑现的硬门禁**，避免投入数日后才撞墙。

**真实案例（Win7 移植评估，结论：不做）**：四层判定的实际结果——

- **Rust 工具链**：1.78 起官方支持基线即 Windows 10（本项目锁 1.90.0）——第一层有硬风险（Win7 为非官方支持档位，需 nightly 自编译标准库），但属工程上可绕过的最大风险，不是「卡点」；
- **系统 API**：`GetDpiForWindow` / `SetProcessDpiAwarenessContext` 为 Win10 专有；
- **WinRT toast**：Win8+；
- **HID++ 电量读取本身**：与 OS 版本无关——协议层从来不是障碍。

评估原文结论是「做独立 Win7 版**可行**，推荐同代码 + 编译开关」，估算约 3~4 人日（编译开关隔离 DPI/toast 路径），硬门禁是：**第 1 天先在真实 Win7 虚拟机上验证最小托盘程序能跑**，跑不过立即止损。「不做」不是做不了，而是维护税与收益权衡后的决策——被否掉的路线是「冻结旧版 Rust + 降级全部依赖」（留下永久维护税）。结论（Windows 10/11 x64）写进根 README 下载段，防止同一问题反复被问。

> 注（2026-10-23）：本条案例中的评估数字与原文细节（估算约 3~4 人日、评估原文结论、四层判定的过程记录）来自仓外评估记录，未入仓，无法经仓库独立复核；可经仓内复核的落点为根 `README.md` 下载段的 Windows 10/11 x64 结论与本条「适用边界」所注评估时点。

**可执行做法**：

1. 移植评估按「工具链 → 系统 API → 运行时 → 业务协议」四层逐层出结论，每层给「支持 / 不支持 / 需绕过」与依据（官方 MSRV、API 文档的最低系统版本）。
2. 给「做」的方案必配第一天硬门禁（最小可行程序在目标平台真机 / 真虚拟机跑通），不过即止损。
3. 「不做」也是正式结论：写清四层依据 + 被否路线的维护成本，落到公开文档（README 系统要求段），一次关闭、不再重议。

**溯源**：根 `README.md` 下载段（「Windows 10 / 11（x64）双击即用」——Win10+ 结论的落点；根 README 无独立「系统要求」段）。

**适用边界**：评估结论随工具链与依赖版本漂移，引用时标注评估时点；本项目评估时点为 v0.3.15 前后。

## E20. 本地文件有界 & 绝不自动删除用户文件

**教训**：常驻程序的本地文件（日志、导出、缓存）必须**全部有界**：单文件有上限或轮转、文件数量不无限繁殖。更重要的红线：**绝不自动删除用户文件**——程序自己写的导出文件，一旦交给用户（另存到用户自选位置）就是用户的，软件无权回收。

**真实案例**：

- **日志运行期轮转（v0.3.15）**：bootlog 原仅启动时轮转，长跑场景单文件可无限增长；改为运行期超过 1MB 即轮转，占用有界。
- **诊断导出改「另存为」（v0.3.15）**：导出从「程序写固定目录」改为用户自选位置，文件名带本地时间戳（形如 `LogiVoltTray-diag-export-YYYYMMDD-HHMMSS-mmm.json`）。
- **用户红线否决自动清理**：曾有方案让导出目录「自动只保留最近 10 份历史文件」，被用户明确否决——「自己选位置会自己管理，删除会影响管理」。该红线随后全链路落实（见 [02 E24](02-collaboration-playbook.md#e24-用户红线全链路传导写进每个环节的验收标准)）。

**可执行做法**：

1. 盘点程序写盘的每个角落（日志 / 导出 / 缓存 / 注册表 / 内存驻留），逐个回答「上界是什么」；答不上来的就是要修的洞。设计文档中把「单文件有界或轮转、文件不许无限繁殖、绝不删除用户文件」写成显式约束。
2. 区分「程序的自留地」（程序全权管理的临时文件，可自行轮转清理）与「交给用户的文件」（导出、报告）——后者只增不删，清理权永远归用户。
3. 审查 diff 时对「delete / remove / 清理 / 保留最近 N 份」字样做专项检索，命中用户文件路径即打回。

**溯源**：`volttray/RELEASES.md` v0.3.15（日志运行期轮转、诊断导出另存为）。

## E27. 派生阈值必须锚定调度源，墙钟派生与调度语义脱钩必出结构性矛盾

**教训**：任何「按时间派生状态」的判定（灰显 / 过期 / 超时），其阈值锚点必须与调度机制同源；改调度模型时，全仓检索依赖旧锚点的派生量一并迁移，不做两套并存。

**真实案例**：GRAY_AFTER=90s 纯墙钟派生与轮询档位（300~7200s，D-66）结构性矛盾，被 v0.3.15「探测轮跳过在线设备」彻底暴露——在线设备 last_success 冻结至下一次整轮，90 秒后误灰显、误报「设备离线」toast、默认图标回退「?」（v0.3.16，D-72）。修复先以「锚 90s 墙钟的临近灰显豁免」过渡，WP-C 落地后统一迁移为「锚本设备 next_due」（D-74「D-72 豁免统一」段），灰显阈值同步改按设备档位锚定——非两套并存。

**可执行做法**：

1. 新增时间类派生量，先写明锚定对象（哪个调度量），答不上来不准合入。
2. 调度模型变更列入「派生量影响清单」：全仓检索依赖旧锚点的判定（阈值 / 豁免 / 展示资格），逐条迁移。
3. 过渡期豁免也要锚调度量而非墙钟；展示层与判定层同权走同一阈值。

**溯源**：`volttray/RELEASES.md` v0.3.16「误报离线修复（D-72）」节；commits `540450a602`、`58b1bd2386`；D-72、D-74。

## E28. 渲染可信性：预览与真实产物单一渲染源，几何与字体度量实测不估算

**教训**：预览与真实产物两套「相似实现」必然漂移、预览说谎；字体与几何的真实墨迹可超估算——居中、缩字、控件宽度都按实测判定，不信宽度估算与硬编码。

**真实案例**：

- **v0.3.18 U-5 单一渲染源**：设置页预览显示背景包裹文字、真实任务栏却溢出（两套实现）。渲染核心开 `render_frame_rgba` 公开出口，设置窗口用当前表单配置临时构建 IconCache 直接渲染——预览 = 任务栏同一张位图的整数倍放大，像素级同源。
- **v0.3.18 U-4 探针画布**：Arial Black @160% 真实墨迹超宽度估算致裁切；改逐像素扫描真实墨迹包围盒（ink_bbox），按 1/8 字高步长收缩（上限 32 次）、按墨迹居中——居中与缩字都不再依赖宽度估算。
- **v0.3.18 U-1 BF-1 单调性**：整数截断下缩字非单调（24px 位图 160% 档字高反比 140% 档矮 1px），改逐档递减收敛并以全矩阵单调不减测试锁定。
- **v0.3.17 R-5 / R-6（同原则）**：导出对话框字体回退栈 EnumFontFamiliesExW 实测存在性（修简体中文乱码）；复选框 GetTextExtentPoint32W 实测宽度 +20% 余量，不再硬编码。

**可执行做法**：

1. 做「预览 X」先找真实产物的渲染出口，没有就先开出口；预览与产物的语义边界（DPI / 主题 / 快照时点）如实标注。
2. 字体依赖列回退栈并逐级实测存在性；几何与宽度一律实测 API 取值，不硬编码。
3. 缩字 / 缩放类逻辑锁单调性测试；渲染断言用像素级测试（墨迹落块）。

**溯源**：`volttray/RELEASES.md` v0.3.18 U-1 / U-4 / U-5、v0.3.17 R-5 / R-6；commits `7c057e685e`、`5ed38b5460`、`23809cc680`、`0ca7223d0e`。

## E29. 前提不成立的计算与告警，删除优于保留

**教训**：告警或计算的输入前提在产品形态下不可获知时，留着只会制造虚假权威——删除优于保留，判断权交还用户。

**真实案例**：v0.3.18 U-6「字色与背景对比度低于 3」警告条——软件在透明背景下无法获知任务栏真实颜色，对比度计算的前提不成立；警告条整体移除（效果用户一眼可见，不需要提醒），设置窗口高度 842→816。

**可执行做法**：

1. 写告警 / 提示前先证明其输入前提可获知；证明不了就不写。
2. 已存在的告警发现前提不成立：删告警、在发布说明写明删除理由，不留「死示例」。
3. 审查 diff 时对「估算 / 假设」驱动的提示类 UI 专项核前提。

**溯源**：`volttray/RELEASES.md` v0.3.18 U-6；commit `2efe946720`；D-82。

## E30. 指向产物的持久外部引用会随换版静默失效：启动期对账自愈，路径比较规范化、保守判不等

**教训**：注册表 Run 键、快捷方式等「写一次就不管」的外部持久引用，在 exe 文件名带版本号升级时会静默失效且界面仍显示正常；等长改名（v0.3.18→v0.3.19）也不能靠长度启发式漏检。路径字面比较必错：必须规范化（大小写 / 斜杠方向 / 长路径前缀 / 尾斜杠 / 重复反斜杠 / 成对引号），无法判定一律保守判不等并收敛重写为规范式——绝不「实际不同却判等」。

**真实案例**：v0.3.19 U-7 启动期「配置 × 注册表」四格对账自愈——配置开 + 值缺失 → 重建；配置开 + 路径已换版 → 重写为当前 exe 完整路径（用户手工附加参数保留）；配置关 + 残留 → 清理；一致 → 不动。自愈成功静默、仅记启动日志一行；失败一次性告警不刷 UI；debug 构建门控跳过一切自动注册表写（门控范围如实披露、不扩大）；8.3 短名 / WSL 大小写敏感目录 / 260 字符 LongPathsEnabled 等固有限制显式划界登记「非本版可治」。配套 24 例跨平台单测、unsafe 块零新增。

**可执行做法**：

1. 凡程序向系统写入的持久引用，清单化登记并设启动期对账点；对账矩阵按「配置 × 存储」四格枚举收口。
2. 路径比较先规范化、纯字符串无 I/O；判不明就保守判不等并收敛重写。
3. 成功静默、失败一次性告警；固有限制显式划界而非隐性遗漏。

**溯源**：`volttray/RELEASES.md` v0.3.19 U-7；commit `e974c736aa`；D-83。

## E31. CI 与门禁自身也是被审查对象：bot 直推受保护分支是反模式，门禁「存在」≠「在跑」

**教训**：bot 持写权限直推 main 既是供应链攻击面，也是「main HEAD ≠ 构建提交」证据错位的根源；门禁不验证了会静默失效——CI 卫生与门禁有效性须按最高优先级立项审查，不是杂务。

**真实案例**：v0.3.17 项目级一审 P0——fmt 从 bot 直推 HEAD:main 改为 `--check` 失败由作者本地修（**本机制取代 E5 所述 fmt 回推机制**，E5 原文保留为历史案例）；CI 权限降 contents:read；新增 pull_request 触发；协议冻结 Python 门禁入 CI。同审发现协议冻结门禁 RED_DIR 指向父目录、常年 FileNotFoundError 无人察觉——一条「存在」的门禁早已不在跑，修复后基线逆推重建、构造差异断言改 difflib 结构性。

**可执行做法**：

1. CI 审查清单：每个 job 权限最小化；无 bot 直推受保护分支；PR 触发；关键门禁在 CI 而非仅本地。
2. 定期验证每条门禁真实执行：制造一次应失败的输入，看是否真拦截。
3. CI 行为变更走正式决策与记录（入 D 条目），顺手改即打回。

**溯源**：`volttray/RELEASES.md` v0.3.17「项目级一审 P0」节；commits `738c8f7a1e`、`2256b31a4e`；D-79。

## E32. CI 红了的处置纪律：fix-forward 并给语义等价证明；跨环境验等价用 tree SHA，不用 commit 哈希

**教训**：CI 失败的修复一律新增提交、不 rebase 粉饰历史；修复提交要做到语义等价可证明；跨环境验证「内容相同」时选对比较锚——commit 哈希含 committer 时间戳不可比，树对象 SHA 逐位可比；推送通道的机制约束（如 Git Data API `force:false` 只许 fast-forward）可直接引用为「历史未被改写」的安全证明。

**真实案例**：v0.3.18 / v0.3.19 各两次提交级 CI fix-forward——rustfmt 重排换行（`15583c7826`、`e702bdec4b`）与 clippy 整数恒等改写（`(s+1)/2`→`div_ceil(2)`：`48676bf138`；`x+1<=n`→`x<n`：`a5e78f1c50`），提交说明均写明「无逻辑变更」，测试逻辑不变；一次跨环境推送复核以树 SHA 逐位比对证明补丁内容一致（commit 哈希因时间戳必然不等，不可作锚）。

**可执行做法**：

1. CI 红 → fix-forward 新提交，提交说明写明等价性论证（仅重排 / 整数恒等 / 测试逻辑不变）。
2. 跨环境验补丁等价一律比对 tree 对象 SHA。
3. 整数算术改写（如手工 div_ceil）必配测试——此类「显然等价」是翻车高发区。

**溯源**：`volttray/RELEASES.md` v0.3.18「验证口径」、v0.3.19「工程约束」节；commits `15583c7826`、`a5e78f1c50`、`e702bdec4b`、`48676bf138`。

## E33. 稳态日志采样带计数，跃迁日志全量

**教训**：全量落盘会让系统性 miss（如蓝牙 / 有线通道的归因失败）刷屏淹没真信号；日志先分两类——「状态没变」采样、「状态变了」全量。

**真实案例**：v0.3.17 R-4 唤醒裁决链落 bootlog——attribution miss 与稳态零信息决策行（归因成功但未装填、保持休眠）采样为每分钟 1 条 + 窗口内压制计数（事后可还原总量）；装填 / 探测 / 失败等状态跃迁行逐条保留。

**可执行做法**：

1. 新增日志点先归类稳态 / 跃迁。
2. 稳态采样必须带压制计数，不能只丢不记；跃迁行不采样。
3. 采样参数（窗口、频率）写进发布说明或决策记录，可复核。

**溯源**：`volttray/RELEASES.md` v0.3.17 R-4；commit `a1594fb54b`；D-77。

## E35. CI 的静默失败面：表达式属性笔误求空无报错，包级依赖扩面会横向改变全部构建目标的系统依赖

**教训**：两处「不报错的错」——GitHub Actions 表达式里不存在的属性（`github.runId`，正确为 `github.run_id`）求值为空字符串而非失败，下游拿到的是空链接；Cargo 包级依赖对全部 bin 生效，给 fuzz crate 加两个本地依赖即让最早存在的目标也开始编译 hidapi（需系统库 libudev），只跑过旧目标的 nightly 环境当即构建失败。两者都让链路在「配置看起来没问题」的状态下产出空结果或直接失败，发现依赖下游症状（issue 正文链接为空 / nightly 红）。

**真实案例**：issue #16（2026-10-24 nightly fuzz 失败自动开单）双根因——① E16 fuzz 扩面（battery/stats/config 三目标）给 fuzz crate 加了 device/app 依赖，frame_fuzz 随之开始编译 hidapi，nightly 的 fuzz-smoke 此前只跑 protocol、未装 libudev 即构建失败（日志实证 Unable to find libudev）；② 自动开单模板 RUN_URL 用 `github.runId` 求空，issue 正文 run 链接为空。修复：nightly.yml 补装 libudev-dev/libusb（与 ci.yml 已实证步骤同款）；`github.runId`→`github.run_id` 全量 4 处。复跑验证：同 commit 的 ci.yml fuzz-smoke 全绿（证明仅缺系统依赖步）；v0.3.23 发版门禁的 fuzz-smoke job 实跑全绿。

**可执行做法**：

1. workflow 里写表达式属性名后，用一次真实触发核对输出非空——空字符串不报错。
2. 给多 bin crate 加包级依赖时，核查最老构建目标的系统依赖面是否变化（cargo tree 对比 / 全部 bin 试编译）。
3. 同一故障先分「构建链失败」与「报告链失败」两条线独立归因，再合并处置；修复以同 commit 等价链路的绿灯为证据。

**溯源**：issue #16；`volttray/RELEASES.md` v0.3.23「issue #16 根因标注」节；commit `cd77a925fd`。

## E37. 签名链启用：先 dry_run 演练全链（零真实产物），工具支持与权限分层逐项实证

**教训**：发布签名链涉及「密钥配置（Secrets 写权限）→ 工具安装 → 签名 → 公钥自验 → 资产上传」多环节，任何一环的首次实战失败若发生在正式发版里就不可逆；给发布 workflow 加 dry_run 演练护栏（走完构建 / 签名 / 自验全部步骤但跳过 Release 创建与上传），先在零真实产物前提下暴露问题。四类暗礁被演练拦下：① 令牌权限分层——Actions 触发可用（204）≠ Secrets 写可用（403），逐项探、403 即停手上报、授权后续跑；② 工具清单「按公开清单采用」不等于可用——taiki-e/install-action 公开清单外的 minisign 在 windows runner 直接报不支持，fallback cargo-binstall 也失败，改官方预编译包＋sha256 钉死才闭合；③ shell 环境差异——git-bash 的 GNU tar 不能解 zip（需系统 bsdtar），且盘符路径会被 tar 当远程主机（--force-local 背景）；④ GITHUB_PATH 只对后续步生效，同步内冒烟要用全路径。

**真实案例**：v0.3.23 发版前 E18 签名链演练（2026-10-24）：release.yml 加 workflow_dispatch dry_run 输入（tag push 时 inputs 为 null、条件恒真，正式行为零变化）；首轮演练因令牌缺 Secrets 写权限阻塞（403，按纪律未重试未绕过、如实上报），授权后续跑；第二轮实证 install-action 不支持 minisign（log: "does not support minisign" → cargo-binstall "no binaries specified nor inferred"），修复为官方 win64 预编译包（sha256 钉死，本地经作者公钥验签）；第三轮实证 git-bash 的 GNU tar 不能解 zip（"This does not look like a tar archive"），改用 Windows 系统 bsdtar（/c/Windows/System32/tar.exe）；第四轮实证 GITHUB_PATH 追加仅对后续步生效（同步内 minisign -v 报 command not found, exit 127），install 步改全路径冒烟、sign 步显式 export PATH（cygpath 转 POSIX）双保险；第五轮 dry_run 全绿（run 40106733568）——install / 签名 / 公钥自验真实执行，两个 upload 步被 dry_run 护栏拦截，零真实 tag / Release 产生，日志零密钥材料命中。fail-open（无密钥跳过照常发布）与 fail-closed（验不过即发布失败）双分支均有日志明文可核。三轮失败各暴露一个真实缺陷、错误互不相同——这正是演练护栏的价值：全部拦在零真实产物阶段。

**可执行做法**：

1. 涉及密钥 / 签名的发布链路，正式发版前必做一次 dry_run 演练，并逐步骤回读日志（不采信「步骤绿了」的自述，要看每步真实执行了哪条分支）。
2. 权限核验逐项来：读 / 写 / 触发分别探一次；403 即停，报清需要用户开哪一项权限。
3. CI 引用的第三方工具在目标 runner 上的支持度，要么实测、要么准备替代路径（官方预编译包＋哈希钉死是最稳的兜底）。
4. 密钥纪律：私钥只进 Secrets，永不入仓库 / 日志 / 评论；公钥入库供用户验签；推送前敏感扫描零命中。

**溯源**：`volttray/RELEASES.md` v0.3.23「工程与质量」E18 条；commits `eca01eb4ea`、`addbb7078c`、`2cc3b086df`、`541afa85d5`、`78b6cb00f8`、`8d6a55890f`、`14fb39fa1a`；dry_run 演练 runs 40101257286 / 40102430268 / 40105000369 / 40105836296 / 40106733568（末轮全绿）；仓库根 `minisign.pub`。

## E39. CI 脚本纪律：job 级工作目录会让相对路径静默错位；「失效不静默」必须配合「异常可见」

**教训**：GitHub Actions job 级 `defaults.run.working-directory` 对步内所有相对路径生效——在 volttray/ 下 `open('docs/...')` 静默错位成 FileNotFoundError；而 `2>/dev/null` 把真实异常吞掉后，治理告警报出错误对象（「时钟数据缺失」），排查需逐层剥。告警的阻断力（exit 1）与异常的可见性（真实错误上日志）必须同时保留，缺后者则「不静默」沦为「报假警」。

**真实案例**：2026-10-25 nightly run 40176674164 转红——fuzz 本体全绿，红的是 E19 批新引入的 30-nights 评审步（该步首次实战即踩坑；前一晚 cd77a925 版还是硬编码起算日、无此步）。修复 b9cdb71：步级 working-directory 钉回仓库根 + 移除 stderr 吞没；workflow_dispatch 复跑 run 40179126476 全绿，评审步正常输出起算日与「未到期」。

**可执行做法**：

1. workflow 步内引用仓库文件，一律步级钉 `working-directory: ${{ github.workspace }}` 或用 `$GITHUB_WORKSPACE` 绝对路径。
2. 失败路径不得吞 stderr；通用错误文案之外必须保留真实异常。
3. 新增 CI 检查步首次实战前，用 workflow_dispatch 在同 HEAD 手动触发一次验证，别等定时首跑。

**溯源**：commits `8c820b5`（引入）→ `b9cdb71`（修复）；runs 40176674164 / 40179126476。

## E40. 复核必须独立取证：成员自述失实是常态而非例外

**教训**：同一天两起自述失实被复核纠正——实施成员断点评论称「仓库无 CI workflow 配置」（实际 6 个 workflow，当天同仓另一批推送后 CI 刚全绿）；偏差声明称「融合稿未规定其它冲刷时机」（规格 §5 明确写了 boundary/run_stop）。两处均非恶意，是上下文不足凭印象作答。复核制度的价值正在于独立取证：API 拉 diff、读规格原文、复跑验证。双独立复核（2026-10-25 用户定稿）首跑即验证价值——两席互不通气各自实证，独立命中同一 P2（规格外斜率过滤）。

1. 复核人必须自行取证（API / 快照 / 实跑），不得采信实施者评论。

3. 双席定级分歧取高从严；「需修改但不阻断已合入」与「附条件通过」等价，转修复批收口。

**溯源**：2026-10-25 双席复核链（自述失实两处 → 双席独立复核 → 条款落库），仓内 commit `2bae826` 可溯。

## E41. 会话交接制度化：HANDOVER 文件必须平台无关、内容自足

**教训**：agent 的跨会话延续有两层——自身持久记忆（工作区记忆文件）与 git 项目沉淀（规则 / 教训 / 登记）。前者换 AI 即失效；后者长期缺「当前状态与待办」这一层——用户一句「你开始任务时从 git 里获取了上一个留下的工作吗」暴露缺口。更深的第二课紧随其后：交接文件初稿引用了平台任务编号与飞书文档链接，用户再问「另一个 AI 不在一个平台呢」——平台专属线索对跨平台接手者是死链。**交接文件必须自足：接手必需的信息直接写在 git 里，平台线索只能作为「同平台补充、跨平台忽略」的附带项。**

**可执行做法**：

1. 交接文件五要素＝状态快照（版本 / HEAD / 未发版内容）＋待办全景（代码窗口 / 等用户事项 / 常态运行，每项含足够落地的实质内容而非外部指针）＋红线纪律＋平台操作要点＋接手顺序。
2. 文件内写明「本文件自足」与「本文件为最新状态口径，历史细节查 RELEASES.md」。
3. 凭证永不入库、只写获取方式（向用户索取）。
4. 触发时机：用户要求收尾、换 AI 接手、长间隔暂停前必做；每次收尾更新。

**溯源**：2026-10-25 用户指令（资源告急收尾到 git）与用户指正（跨平台死链）；docs/HANDOVER.md 首批创建后按本课退回修正为自足版。

## E42. 派发即冻结：任务描述更新对已启动的执行不生效

**教训**：向执行成员覆盖更新任务描述时，若其执行已经启动，成员拿到的仍是启动时刻的旧文本——描述更新只影响下一次执行。实例：2026-10-25 收尾落库批，执行 19:50 启动，主 AD 20:07 用「自足版」全文覆盖任务描述，成员推送的仍是 19:50 旧稿，验收逐字回读才暴露（退回修正）。

**可执行做法**：

1. 更正规格必须在成员开工前完成；开工后发现规格要改，宁可叫停重派，不要指望描述覆盖生效。
2. 派发描述中写明「正式动手前先回读本任务描述最新版，与启动时读到的不同则以最新为准」。
3. 验收侧：凡中途更新过描述的批次，验收时先核对产物依据的是哪一版规格。

**溯源**：2026-10-25 收尾落库批推送旧稿验收退回事件（同平台任务线索，跨平台忽略）。
