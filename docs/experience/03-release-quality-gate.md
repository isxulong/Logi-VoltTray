# 发布质量门禁清单

> 每次发布前逐条核验，任何一条不过就打回，不打折扣。
> 本清单是 E5（CI/GitHub 实战）、E7（证据优于自述）、E9（质量门禁）三条经验的清单化落地，按本项目发布流程组织，其他项目可照结构改造。

## A. 版本与提交

| # | 核验项 | 怎么核 | 不通过的典型形态 |
| --- | --- | --- | --- |
| A1 | 版本号升级为**独立 chore 提交** | workspace `Cargo.toml` 的 `workspace.package.version` + `Cargo.lock` 同步，只动版本 | 版本号夹在业务提交里顺手改 |
| A2 | tag 指向该 chore 提交 | `git ls-remote --tags` 或 API 比对 tag 的 commit sha | tag 指在 chore 之前的提交上 |
| A3 | tag 与发布 diff 内**无业务代码混入** | 对 tag 与上一 tag 做 diff，确认只有版本号与 lock 变化 | 「顺手修个小问题」混入发布 |
| A4 | 版本号一处修改、全仓生效 | 确认 workspace 统一 `version.workspace = true`，无 crate 单独漂移 | 某 crate 版本号忘了升 |

## B. CI 与构建

| # | 核验项 | 怎么核 | 不通过的典型形态 |
| --- | --- | --- | --- |
| B1 | CI 全绿，且 green run 的 head_sha **就是发布提交** | 查 runs 列表按 head_sha 过滤 | 引用了一个「别的提交」的绿灯 |
| B2 | **fmt 自动回推错位已对齐**：若 main HEAD 比构建提交新一个无 CI 的格式化提交，用整树 diff（token 多重集比对）证明语义等价，并在交付中写明 | 对比两个提交的整树。实操：`git diff --name-only <构建sha>..HEAD` 应只列出被 fmt 重排的文件，再对这些文件 `git diff -w`（忽略空白）比对为空即语义等价；无 git 环境时走 GitHub compare API 取两提交的文件列表与 patch 核对 | 拿「HEAD 全绿」当构建提交的证据 |
| B3 | EXE 内嵌版本资源（FileVersion / ProductVersion）与发布版本一致 | 下载产物查文件属性版本 | 版本资源停留旧版（本项目 v0.3.8 起由 `CARGO_PKG_VERSION` 派生，防手工脱节） |
| B4 | 构建产物来源可追溯 | 记录 CI run / 构建提交 / 下载渠道 | 「本地随手 build 的包」进 Release |
| B5 | **Windows 专属改动已过本地交叉验证**：触及 `cfg(windows)` 代码的提交，推送 CI 前已按 Windows target 本地 `cargo check` + `clippy`（如 zig 交叉 `x86_64-pc-windows-msvc`） | 看修复 / 提交记录中的交叉验证说明，或自己复跑 | Linux 侧全绿、Windows CI 第一次编译就炸（v0.3.15 首个 CI run 的 clippy 失败，详见 [01 E16](01-engineering-lessons.md#e16-windows-专属代码合并前必须本地交叉验证别把-ci-当第一道编译器)） |

> 注（2026-10-19）：B2 所述「fmt 自动回推」机制已自 v0.3.17 起废除（改为 `cargo fmt --check`、不一致即失败由作者本地修复，见 D-79 / [01 E31](01-engineering-lessons.md)）；此后发布不再产生「回推错位」。B2 原文保留为历史核验记录——v0.3.16 及更早版本的放行取证仍按本条核验。

## C. 产物校验（证据优于自述）

| # | 核验项 | 怎么核 | 不通过的典型形态 |
| --- | --- | --- | --- |
| C1 | 附件哈希**三方一致**：发布者报告、审查者亲算、交付者复验 | 各自独立下载、独立算 sha256，三方比对 | 直接引用别人贴的哈希值 |
| C2 | 测试数等关键数值从**产物 / 源码实测读取** | 本地跑 `cargo test --workspace` 实测计数 | 从 CI 汇报里抄数字（CI 日志接口可能 403 拿不到） |
| C3 | 下载渠道受阻有备选 | artifact 直连 401 时用免登录镜像（如 nightly.link）下载比对 | 因一个端点失败就跳过校验 |

## D. 发布说明与验证分级

| # | 核验项 | 怎么核 | 不通过的典型形态 |
| --- | --- | --- | --- |
| D1 | Release 说明面向用户：中文，讲「**能干什么 / 修了什么 / 要注意什么**」 | 通读说明 | 按技术模块罗列内部改动 |
| D2 | **未验证项单列**：已验证 / 部分验证 / 未验证 / 阻塞 分级如实标注 | 检查说明中是否有未验证段 | 任何失败、跳过、过期证据被润色成「通过」 |
| D3 | 红线逐项确认未被触碰（本项目：零鼠标电池——无对休眠设备的主动查询 / 保活） | 对 diff 逐条过红线 | 新逻辑在休眠路径上加了主动探测 |
| D4 | 升级注意事项写明（如：先退旧版再启新版；不兼容变更给迁移说明） | 通读说明 | 破坏性变更无声发布 |
| D5 | **默认值 / 显示行为突变面须在 Release 说明头部作兼容性声明**：本版若改了默认值或产生用户可见的显示行为突变，说明头部须有兼容性声明段（迁移规则 + 突变面逐条 + 误伤面披露） | 通读说明头部；对照本版 diff 中的默认值与显示行为变更 | 行为突变只散落在条目正文、或无声发布（v0.3.18 头部声明为正例。与 D4 边界：行为突变**声明**置头部兼容性段，升级**操作步骤**置 D4 升级注意事项段，二者互相引用） |

### 门禁拦过的真实问题（保持清单诚实的证据）

- **v0.3.9 打回（P1）**：多设备同睡误判死句柄 → 违反零鼠标电池红线，返工后以 v0.3.10 发布（详见 [01 E3](01-engineering-lessons.md#e3-hid-协议与鼠标休眠的工程现实)）。
- **fmt 错位取证**：交付二进制的构建提交 ≠ main HEAD（fmt bot 自动回推），用整树 diff 证明语义等价后在交付中说明（详见 [01 E5](01-engineering-lessons.md#e5-ci--github-实战陷阱沙箱与-api-环境)）。
- **测试数取证**：CI 日志接口 403 时改用「源码实测 + CI test 步骤绿灯」交叉口径，并如实标注未验证边界（详见 [02 E7](02-collaboration-playbook.md#e7-证据优于自述第一原则)）。
- **v0.3.15 首个 CI run 打回（clippy）**：Linux 侧全绿的提交在 Windows CI 首次编译 `cfg(windows)` 代码即报 5 文件错误（windows crate 模块路径、`OPENFILENAMEW` 无 `Default`、闭包逃逸等）→ 催生门禁 B5（本地交叉验证前置），详见 [01 E16](01-engineering-lessons.md#e16-windows-专属代码合并前必须本地交叉验证别把-ci-当第一道编译器)。
- **T6 红队 P1 打回（数据完整性）**：设备身份晋级路径采信别名槽位冻结的 unitId，RF 重配对场景下会把 A 鼠标的台账绑到 B 端点 → 必修「晋级前重新验明 unitId」后放行，裁决原话「数据完整性风险不用进度换」（详见 [01 E17](01-engineering-lessons.md#e17-设备身份必须锚定物理设备而不是某次枚举的通道快照)）。
- **v0.3.16 修复 WP-C 交付代码 7 处 Windows 编译错误**：tray crate 此前从未通过编译（timelocal.rs 模块路径、rawinput.rs RID_HEADER / Option<HANDLE>、main.rs 传参与作用域）——B5 本地交叉验证门禁再次实证其必要性（详见 `volttray/RELEASES.md` v0.3.16 修复节、D-75）。
