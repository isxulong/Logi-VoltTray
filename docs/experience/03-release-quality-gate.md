# 发布质量门禁清单

> 每次发布前逐条核验，任何一条不过就打回，不打折扣。
> 本清单是 E5（CI/GitHub 实战）、E7（证据优于自述）、E9（质量门禁）三条经验的清单化落地，按本项目发布流程组织，其他项目可照结构改造。

| A4 | 版本号一处修改、全仓生效 | 确认 workspace 统一 `version.workspace = true`，无 crate 单独漂移 | 某 crate 版本号忘了升 |

- **v0.3.9 打回（P1）**：多设备同睡误判死句柄 → 违反零鼠标电池红线，返工后以 v0.3.10 发布（详见 [01 E3](01-engineering-lessons.md#e3-hid-协议与鼠标休眠的工程现实)）。

## G. 红线守卫（advisory）

P2-7（相位一）：删除类调用的静态模式检查以 **report-only** 形态挂 CI——`ci.yml` `redline-guard-advisory` job（`continue-on-error: true`，仿 actionlint advisory 先例，红只在 run 页留痕、不阻断任何提交）。检查项：① 裸调用（`std::fs::remove_file` / `remove_dir` / `remove_dir_all` 未经 `let _ =` 兜底）；② 删除调用同行参数命中用户文件路径特征（config_dir / data_dir / home_dir / 用户）。红线锚点：E20「绝不自动删除用户文件」。

**基线**（2026-10-22 本地实测，方法与 job 内一致）：`volttray/crates` 内删除类调用共 54 处（含 `tray/src/main.rs` 8 处，该文件须 `grep -a` 否则被二进制误判漏检），全部 `let _ =` 兜底形态，①② 均 0 命中；裸调用与用户路径命中的正向捕获能力已经注入用例反向自证。

**命中 / 误报统计口径**：每版发布对账时读取该期 `redline-guard-advisory` run 页——命中数＝①+② 报出的行数；误报数＝人工复核确认安全的行数；误报率＝误报数÷命中数（命中数为 0 记「无命中」）。结果记入 06 度量登记行表的**备注列**，不新增指标。已知误报/漏报源（复核时按此豁免、不另开单）：多行续行（调用拆行后首行含 `let _ =`、续行不含，会被①误报）；同一行混合兜底形态（裸调用与兜底调用同行，①会漏报）——两者都指向「行级静态检查的固有边界」，升级评审时一并权衡。

**口径上限（C-07 登记）**：本检查只覆盖**字面特征形态**——`let _ = std::fs::remove_file(p)`（p 实为用户路径、但行内无 `config_dir` / `data_dir` / `home_dir` / `用户` 字面特征）这类「语义命中、字面无特征」的样本，①② 双检查均不可见（2026-10-22 注入实证，见 PR #10 描述留档）。评审与对账读数时不得把「零命中」读作「无风险」。

**升级条件**（C-07 修订，三项同时满足方可进升级评审）：① **注入用例每版回归通过**——每版对账时重跑注入样本（裸调用、用户路径字面命中各一），①② 双检查按预期捕获；② **≥1 次真实命中处置记录**——防止结构漏检下的「连续零命中」平凡满足旧判据（零命中不构成检查有效的证据）；③ **混写形态全仓 grep 为零**——`let _ =` 与裸调用同行混写、多行续行等已知漏检形态全仓检索为零。三项齐备后评审是否升为必过门禁（评审走 06 对账区，与 actionlint 升级评审同法）。在此之前本检查不阻断任何提交。

**候选收益（未验证）**：「拦截 v0.3.9 类 P1」为静态检查的候选收益判断，未经真实拦截事件验证，不写成实测。

## H. 失效模式分诊方法论（相位二）

按失效发生的阶段选**最便宜的拦截手段**，不为所有失效统一上最重的那道：

| 阶段 | 典型失效 | 最便宜有效拦截 | 本项目落点 |
| --- | --- | --- | --- |
| 构建期 | 某平台从未编译过（D-75 类） | 该 target 的交叉 `cargo check` 进 CI | ci.yml ubuntu job windows-target 步 |
| 发布契约 | 资产名/数量漂移、sha256 缺失、自启路径写错（U-7/D-83 类） | 发布流水线静态断言（不跑真机） | release.yml `release-contract` 步（D10） |
| 协议层 | 编解码行为漂移 | 黄金向量 + 冻结测试（纯编解码，零硬件） | `python -m unittest discover -s tests` + fixtures/golden |
| 运行时硬件 | 真机握手/唤醒/枚举失效 | 真机 runner 或 uhid 回放（最贵，最后上） | 缺口登记见 D+ 节，真机 runner 上线前排期评审 |

原则：失效在哪一层发生，就在那一层的门禁拦——下层门禁绿了不代表上层
安全（Linux 全绿 ≠ Windows 能编译），上层门禁也不必为下层已拦的失效
重复设防（协议冻结测试保留不退役，CI 门禁健康断言只查向量目录存在性
与新鲜度，不重放全量向量）。

## I. 双独立复核签发前执行清单

> 规格的单一来源为 [docs/ai-orchestration.md](../ai-orchestration.md) ③ 巡检清单「代码批次质检复核——所有代码批次实行双独立复核」条款；本节只放执行清单，经验库内不复制规格全文。

签发前逐项打勾：

1. 批次归类已显式声明并留痕（纯文档批次豁免，或双独立复核适用）；
2. 两席（全栈代码质检官、高级开发工程师）使用同一份复核清单（本文件门禁清单＋本批次任务书验收项），各自独立取证、各自独立出具复核报告，互不通气；
3. 放行口径核对：两席均放行才算通过；两席均否决即终局否决；一放一否由主 AD 按证据书面裁决并留痕；
4. 利益回避核对：实施者未充当复核人；主 AD 与实施者重合时，分歧裁决已升级用户；
5. 一席不可用时批次按「挂起」处理并按巡检条款推送用户，不静默卡死。
