# 发布说明

## v0.3.14

通知/闪烁三故障（v0.3.13 真机反馈）修复 + 红蓝对抗审查必修项收敛。修复分支经红队攻击审查与蓝队独立走查，本版含两队共识缺陷与红队 P1 的全部处置（处置对照见发布任务评论）。

### 修复

- **现象①「静默通知无用 / 调阈值不生效」**：「静默通知」实际只控制 toast 提示音（不管弹窗、不管闪烁）——菜单文案改为「通知静音（仅关提示音）」澄清（配置键不变，向后兼容）；阈值热改后立即按最后已知读数重估低电态（`LowBatteryTracker::evaluate_now`，旧逻辑默认档最长约 1 小时才体现）；TOML 热重载补 ~5s 节奏 mtime 补查（旧逻辑一轮轮询才查一次，默认档最长约 30 分钟）。
- **现象②「关了再开不闪」**：右键开菜单此前会误触发停闪锁存（任何 Click 都停闪），改为仅「左键按下」停闪；新增「关→开」沿重武装——重新打开闪烁开关即清除停闪锁存、立即恢复。
- **现象③「两种频率叠加闪烁」**：SetTimer 丢弃的系统分配 timer id 现被捕获，消息泵按「真实 id + NULL hwnd」双重过滤——设置窗口 tooltip 的 ~100ms 定时器不再驱动闪烁相位；KillTimer 用真实 id 对称释放。
- **B1（红蓝共识，必修）：阈值调高进入的低电期 toast 永久丢失**——阈值热改触发即时重估后，重估告警此前被丢弃且 tracker 已置 active，本次低电期 toast 永不再发（只剩闪烁）。现重估告警进入 pending 队列，由 GUI 侧走与轮询路径相同的 toast 派发（含通知总开关/静音配置）；去重由 tracker 状态保证，每个低电期至多一条。
- **B9（红蓝共识，必修）：可观测性补齐**——设置应用落 bootlog（含键级 diff：阈值/闪烁/静音/通知/轮询/自启/外观）；闪烁启停落日志（start / stop + 停闪原因：用户单击 / 开关关闭 / 低电解除）；toast 派发 / 抑制 / 失败落日志（此前失败静默吞掉）；菜单三项开关切换落日志。真机导出从此能看到「改没改上、闪没闪、通知发没发」。
- **B2（蓝队必修）：重启/自启后低电提醒态丢失最长约 30 分钟**——进程内设备首次成功读数（注册探测）立即按当前阈值即判（主机侧零射频），消除默认 1800s 轮询档下「第 2 次读数才恢复提醒」的盲区；同时消除恢复时 toast 重发。取舍（已裁决）：首读数放弃 2 连击去抖，极端情况下一次异常首读数可能立即告警一次；后续读数恢复 M11 去抖语义。
- **B3（蓝队必修）：单击停闪被休眠/唤醒冲掉**——设备灰显/休眠期间不再改写低电闪烁态（休眠并非低电解除），停闪承诺保持到本低电期真正解除；唤醒后由 tracker 重新裁决，不再违背「我明明停过」。
- **B7（红蓝共识）：设置窗每次打开落「类注册失败」误导日志**——RegisterClassW 返回 0 且错误码为「类已存在」（重复打开窗口的正常路径）时不再记失败；仅真实注册失败留痕。

### 延期 / 待办（红蓝裁决留痕）

- P1-3/B8「槽位注销后 30s 重扫无退避」：是否对休眠设备产生射频唤醒未经真机证实（蓝队判「不判独立 bug」），贸然加退避会拖慢被注销设备的自动恢复——延期，列入真机验证项后下版本处置。
- P2-1（后台设备阈值热改不即时，下一读数同步）、P2-2（拔电后立即改阈值的 stale charging 边界）、P2-3（热改绕过 5% 迟滞，注释声明的设计取舍）、P2-4（非原子配置写）、P2-5（轮询间隔不热生效）、P2-7（core Mutex 横跨整轮 HID I/O，pre-existing 性能项）、B4/B5（通知总开关 UI + 总静默语义，随下版本一起做）、B6/P3-3（SetTimer 失败兜底泵）、P3 余项与 B10/B11：延期 / 列入待办。

本版全部修复为主机侧状态判定与日志（内存重估、文件 mtime stat、共享内存直写、bootlog 追加），**未引入任何对设备的主动查询**；休眠设备 Skip 语义（D-33）不变。

## v0.3.12

诊断导出增强（D-69）：真机实证——重启后识别失败时，导出的诊断 JSON 只有空数组 `[]`（旧格式 = 裸设备事件流数组，零设备时毫无信息量），远程排障还要二次索取 logi-volttray.log。本版把导出重构为对象，一次导出即带齐「设备事件流 + 日志尾部 + 最近枚举现场」。

### 修复

- **导出 JSON 由裸数组重构为对象（不兼容变更，向后兼容说明）**：旧格式是设备事件流的裸 JSON 数组（`[...]`）；新格式为对象，原事件流整体迁入 `devices` 字段（脱敏逻辑不动，P1-6 语义不变）。旧读端若直接把顶层当数组解析会失败——请改为取 `devices` 字段。新结构：`devices`（原设备事件流，锁中毒降级为空数组 + `devices_reason`）；`log_tail`（日志尾部 `{path, lines, reason}`，约 200 行）；`last_enum`（最近一次枚举快照，见下）或 `null`；`exported_at`（Unix 秒）；`app_version`。
- **`log_tail`：logi-volttray.log 尾部约 200 行**（`LOG_TAIL_MAX_LINES=200`）。三态语义：正常 → `lines` 尾部 200 行（顺序保持）；文件不存在 → `lines: []` + `reason: "log file not found: ..."`；文件为空 → `lines: []` + `reason: "log file is empty"`；其它 I/O 错误 → 空数组 + reason。**任何情况下导出不因此失败**（v0.3.2 「os error 3 让导出整体报错」教训：子项降级，不整体抛错）。
- **`last_enum`：最近一次枚举快照（内存状态）**：IO 线程每轮枚举后写入 `{at_ms, forced, candidate_channels, channels[{key, pid, tag, open, error}], registered_slots, error}`——候选通道数、各通道 open 结果（ok / failed / cached / reopened / cached-reopen-failed，含错误原因）、已注册槽位数、HidApi 初始化失败原因。导出时直接读内存，不打扰设备（零射频）；从未枚举（如导出先于首轮枚举）为 `null`；锁中毒降级为 `null` + `last_enum_reason`。快照写入锁中毒则本轮跳过，绝不影响主流程。
- **导出永远成功**：devices / log_tail / last_enum 任何子项失败各自降级为空 + reason 字段，导出整体永不报错；最终序列化失败兜底 `"{}"`。

### 零鼠标电池约束

导出为纯读操作：读内存（observer 事件流、枚举快照）+ 读日志文件，不对设备发起任何 HID 查询，零射频。

### 未验证项

tray 层（Windows 专属代码）无法在 Linux CI 编译之外的本地环境验证，Windows 运行时行为（菜单导出、枚举快照写入、日志路径解析）待真机验证；`read_log_tail` 三态（缺失/空/正常 250 行取尾 200）、快照 null/非空序列化、devices 脱敏保持已由 app 层单测锁定（6 例，diag_export.rs）。

## v0.3.11

真机复盘锁定的「重启后 0 槽位 + 死缓存句柄」死锁修复：重启后槽位注册不上时，活性裁决（ChannelLiveness）的轮询 outcomes 恒为空、永不裁决，缓存句柄永不重开，30s 重扫永远打在已失效句柄上——托盘永久「?」，唯一出口是手动刷新。本版按复盘 F1+F2+F3 实施；用户真机补充反馈「出日志时鼠标一直没动、处于休眠」后，F5（动鼠标立即恢复）由暂缓提为必做，连同质检复审指出的 P3 一行修复并入本版（F4 活性裁决与轮询档位解耦仍留待排期确认）。

### 修复

- **通道级「扫槽连败」裁决（F2，核心）**：新类型 `volttray-app::reconnect::SlotScanStreak`（每通道一个实例，纯逻辑单测覆盖）——连续 3 轮「全部槽位扫描失败且至少一次 I/O 类错误」即对该通道**强制重开句柄**；重开失败则整通道作废 + `invalidate_handles` 走全量重枚举。**跨槽位去重、按轮裁决**：一轮 7 个槽位全败只记 1 次连败；任一槽位注册成功即清零；本轮零扫描（槽位已满）冻结。**纯超时（无 I/O 错误）不得触发重开且连败清零**——设备深睡不应答不是句柄死亡（v0.3.10 P1 质检打回的同族陷阱）。
- **握手失败类别透出（F1，纯可观测性，不改行为）**：`Handshake::NoResponse` 携带 `NoResponseCause`（Timeout / Io / Protocol），此前 `Err(_)` 同判 NoResponse；slot scan 日志区分 `handshake no response`（超时/协议类）与 `io error (handle suspect)`（I/O 类）——死句柄与深睡设备在日志中可分辨。
- **无设备态重扫汇总日志（F3）**：每轮重扫落一行 `rescan round N: channels=n slots=0 cached_handle reopen=yes/no`，与枚举签名去重独立（死锁场景候选集合不变、签名去重不落盘，此前死锁期间完全无观测）；单会话上限 100 行防爆量。
- **动鼠标立即恢复（F5，真机反馈补充）**：唤醒信号此前只 arm 已注册设备（`sleeping_ids`）的探测资格，未注册设备收不到任何信号——重启后鼠标在睡、槽位空时，用户一动鼠标要等下一次退避重扫（最长 120s）才可能恢复。新增 `Reconnect::request_wake_enum`：Raw Input 唤醒事件到达且当前注册槽位为 0 时置 force，下一轮循环立即强制重枚举+扫槽（主机侧发起；此时鼠标已被用户物理唤醒、处于活跃态，属「设备已醒时补读」，不违反零鼠标电池红线——红线禁止的是主动唤醒休眠设备）。防抖：距上次唤醒触发不足 `WAKE_ENUM_MIN_INTERVAL`（5s）的事件合并（GUI 侧另有 2s 合并），事件风暴不形成枚举风暴。已有注册槽位时维持原路径（只 arm 探测资格，不触发枚举）。
- **scrap 分支 force 被同轮清掉（P3，质检复审）**：扫槽连败且重开失败作废整通道时，`invalidate_handles` 此前发生在同轮 `record_result`（无条件清 force）之前——「立即重枚举」退化为下一个 30s 枚举门控点。现移到 `record_result` 之后置位，下一轮立即全量重枚举。

### 零鼠标电池约束

F2/F5 的强制重开与强制重枚举是主机侧 HID API 操作，零射频；**不对判定休眠的设备发起任何主动查询**（休眠槽位 Skip 语义不变，D-33）；F5 只在 Raw Input 已观测到鼠标活动（= 用户行为本身产生的射频流量，零额外成本）时触发。需要说明的既有行为：无设备态的周期重扫（有接收器通道时 30s 一轮）会对**未注册槽位**发起扫槽握手——这是 v0.3.9 以来「槽位注册不上时的发现机制」，每轮每槽位仅 1 个 ping 帧（应答成功才继续 feature 探测）；对已注册的休眠设备一律 Skip、零主动查询的本红线语义不变。

### 未验证项

tray 层（Windows 专属代码）无法在 Linux CI 编译之外的本地环境验证，上述 Windows 运行时行为（连败触发重开、重开失败作废、汇总日志、唤醒事件触发的强制重枚举与风暴合并）待真机验证；裁决逻辑已由 app 层单测锁定（连败触发 / 纯超时不触发 / 重开失败作废 / 跨槽位去重按轮裁决，4 例；F5：零槽位触发 / 有槽位不触发 / 风暴合并，3 例）。

## v0.3.10

v0.3.9 质检打回返工：多设备同睡误判死句柄（违反零鼠标电池红线）、「立即刷新」首次点击不生效，以及三个健壮性项。

### 修复

- **通道级超时连击改按「轮」裁决（P1，核心）**：v0.3.9 按「次」累计且跨槽位不去重——同一接收器挂 ≥2 台设备同时休眠时，第 2 轮轮询就把正常休眠误判为句柄死亡，导致设备假离线、槽位缓存作废，且此后每 30 秒对休眠槽位主动 HID 握手探测直到物理唤醒（v0.3.8 同场景零查询，违反零鼠标电池红线）。v0.3.10 改为：**整轮零应答才记 1 次静默连击**（一轮内任一槽位成功或回了字节——错误帧也算——即清零；本轮无可查询槽位则冻结），连续 3 轮全静默才判句柄死。裁决逻辑下沉 app 层 `volttray-app::reconnect::ChannelLiveness`（纯逻辑，单测覆盖「多设备通道部分槽位休眠不判死」「整轮零应答才累计」「任一应答即清零」回归断言）。
- **「立即刷新」第一次点击即生效（P2，用户主诉场景）**：强制重枚举轮（刷新/句柄失效触发）对已有通道**一并重开句柄**——通道 key 不变不代表缓存句柄活着（接收器同口重插/驱动重载后旧句柄已死）；v0.3.9 只在死句柄上补扫槽位，需累计 3 次失败才自愈。重开失败保留缓存句柄，由活性裁决在后续轮次判死并自愈。
- **设备级硬失败不再误伤同通道健康槽位（P3）**：错误帧/映射失败/特性缺失等设备级错误 3 连败恢复 v0.3.8 语义——只注销本槽位（30s 内随重枚举重扫恢复）；整通道作废只由活性裁决按轮判定（io_error 作为句柄级证据参与裁决）。
- **枚举日志签名去重（P3）**：正常态每个轮询周期（默认 1800s）发生一次的例行枚举（30s 仅为重枚举门控下限，reconnect.rs REENUM_INTERVAL）在候选集合未变时不再全量落盘，仅集合变化或枚举失败时记录，与「只记状态变化与失败」口径一致（单会话日志体积有界）。
- **唤醒探测超时单独计数（P3）**：设备已知休眠后，唤醒探测静默是常态（深睡唤醒慢）——单次探测超时不再判死整通道（v0.3.9 会整通道重建、设备假离线后 ≤30s 自愈），连续 2 轮探测全静默才判死（`WAKE_PROBE_INVALIDATE_THRESHOLD = 2`）。

休眠设备保持注册休眠态、一律 Skip、零主动查询（D-33 语义不变）；不再存在「误判作废 → 每 30s 主动握手探测休眠槽位」的破口。句柄重开/重枚举均为主机侧 HID API 操作，零射频。

## v0.3.9

真机「系统重启后无法识别电量（托盘 ?）、手动刷新无效」修复：HID 设备识别/查询层的重枚举与自愈。

### 根因（重启后 ? 且刷新无效的原因）

代码层面四个怀疑方向全部命中（v0.3.8，详见 docs/decisions.md D-65）：

- **「立即刷新」不重新枚举（主机制）**：刷新只重跑一轮电量查询，枚举受 30s/通道非空门控，有缓存通道时「刷新」= 拿旧句柄重查一遍——句柄已死则怎么刷都是 ?，正好解释「手动刷新也无效」。
- **句柄缓存无失效路径**：重启/接收器重插/驱动重载后缓存的 HID 句柄已死，槽位 3 连败只注销槽位、通道死句柄保留，永不自愈。
- **启动时序竞争**：开机自启早于 USB 接收器/驱动就绪，首次枚举 0 设备；旧逻辑恢复周期长且全程无日志。
- **无设备态无退避**：无设备时等待时间长，且没有任何「进入/退出无设备」的可见事件。

### 修复

- **「立即刷新」先重枚举再查询**：刷新置强制标志，下一轮先走完整枚举（重开句柄、重扫槽位）。
- **句柄失效自愈**：查询连续失败达阈值（3 次）自动作废整条通道（句柄 + 槽位缓存）并强制重枚举——非超时硬失败按槽位连败计数；查询超时在 D-33 休眠语义之外另累计通道级连击（真休眠 2 次即停轮询，不会触发；持续超时 = 句柄已死）。
- **无设备态退避重枚举**：枚举后 0 注册槽位且无候选通道时按 30s/60s/120s 退避重试（仅主机侧 HID 枚举，零射频，不违反零鼠标电池约束）；枚举到设备即退出无设备态、恢复正常轮询。
- **设备层诊断日志**（默认只记状态变化与失败，不逐笔记成功查询）：每次枚举的候选通道数与各候选 VID/PID/路径、通道打开成功/失败及错误、每次电量查询失败原因分类（query_timeout / io_error / error_response / no_battery_features / device_gone，含硬失败 x/3 计数）、槽位扫描握手无响应/探测失败、进入/退出「无设备」态事件——下次同类问题看 `%APPDATA%\LogiVoltTray\logi-volttray.log` 即可定位。
- 逻辑集中于 `volttray-app::reconnect::Reconnect`（纯逻辑，7 个新单测覆盖状态机/强制刷新/失效自愈/退避节奏），版本 0.3.8 → 0.3.9（Cargo.toml + Cargo.lock 同步）。

### 未验证项

- tray 层（Windows 专属代码）无法在 Linux CI 编译，Windows 真机行为（重启后恢复、刷新生效、退避节奏）待真机验证；`reconnect` 状态机逻辑已由 app 层单测锁定。

### 轮询间隔档位按真实耗电数据重排（D-66）

- 档位由 60/300/600/900/1800 秒调整为 **300/600/1800/3600/7200 秒（5/10/30/60/120 分钟）**，默认由 600 秒调整为 **1800 秒（30 分钟）**。
- 依据：罗技 MX Master 3S 官方续航最长 70 天（1% 耗电 X≈16.8 小时）、G502 LIGHTSPEED 官方 55 小时持续游戏（X≈33 分钟），X 跨设备差 30 倍，无法用固定值精确命中「50%X」；轮询本身的鼠标电耗可忽略（一次 HID++ 电量查询仅约 2 个射频短包，60s 轮询一天 1440 次 ≈ 活跃使用约 3 秒的无线电耗），调档理由是「显示新鲜度足够即可」，不是省电。中间档 1800 秒 ≈ 耗电最快游戏鼠标 50%X，办公鼠标任意档都远快于其 X。
- **存量配置自动迁移**：已移除档位迁移到最近新档（60→300、900→600）并写 warning 日志；合法旧值（300/600/1800）原样保留。
- 设置窗口轮询间隔提示如实改写：「轮询本身几乎不消耗鼠标电量（每次查询仅约 2 个射频数据包）；间隔只需保证显示足够新鲜。休眠中的设备不会被主动唤醒查询。」——不再暗示「间隔越短越耗电」。
- 零鼠标电耗硬约束不变：休眠设备不会被主动查询/保活，休眠灰显最后已知电量的语义不动。

## v0.3.8

真机「托盘图标预渲染失败（图标缓存未生成默认帧）」启动退出修复。

### 根因（v0.3.4 正常、v0.3.5 起启动即退出的原因）

- 触发参数**不是字体名**：Windows GDI 对不存在的字体会静默回退系统默认字体，字体名永远不会导致帧生成失败。
- 真正原因：v0.3.5 的配置迁移把旧配置「字体颜色=自动 且 分档未勾选」迁移为**分档模式开启**（这正是日志里 `config loaded, 1 warning(s)` 的那条 warning）。分档模式下图标缓存只预渲染分档色与灰档，**不含默认色档**；而启动首帧（电量未知 "?"）一直固定查默认色档——查不到，v0.3.7 起即弹窗退出。
- v0.3.4 之所以正常：当时旧配置分档关闭，缓存里有默认色档。运行中的图标刷新逻辑本来就正确（分档开启时用灰档），只有启动查询与之失配。

### 修复与容错

- **启动首帧取色与运行时对齐**：分档开启走灰档，未开启走默认档——与电量刷新逻辑同一决策。
- **渲染失败永不杀死程序**：启动时图标帧生成失败，先在日志记录具体原因（哪个档位/文本/哪个 GDI 阶段），再用出厂默认外观配置重试；回退成功则正常启动、托盘可用，并在**首次打开设置窗口时一次性提示「外观配置已回退默认（原因：xxx）」**。仅当出厂默认也失败（疑似系统级 GDI 故障）才弹窗退出。
- **配置警告内容入日志**：配置加载的每条 warning 逐条写入启动日志（此前只有数量没有内容，本次根因正是那条迁移警告）。
- 版本资源（文件属性版本号）改由 Cargo 版本自动派生，杜绝手工同步脱节。

> 给 v0.3.3 / v0.3.4 老用户：本版本不会再因旧配置启动失败；若日志/设置窗口提示外观已回退默认，重新在设置里调整一次外观即可。

## v0.3.7

真机反馈专项：「下载后双击没反应或报错」的启动路径排查，以及启动失败可见化。

### 排查结论（v0.3.4 → v0.3.6 启动路径整树对比）

- 启动主链路（单实例 → DPI → AUMID → 配置 → IO 线程 → 图标缓存 → 托盘 → 消息泵）在 v0.3.5 / v0.3.6 **无崩溃性代码变更**；v0.3.5 新增的 winres 图标资源仅在设置窗口打开时懒加载，ICO 文件实测合法，不构成启动即崩的确定根因。
- 两条**完全静默**的退出路径是「双击没反应」的头号嫌疑：**已有实例在运行时，第二个实例零反馈退出**（旧版本可能还留在托盘里）；以及托盘/图标初始化失败时，release 版（windows 子系统、无控制台）的错误信息无人可见。
- 本版本把所有启动阶段失败变成**必然可见**（见下），若真机仍异常，日志可直接定位卡点。

### 启动失败可见化

- **崩溃日志**：启动全程写入 `%APPDATA%\LogiVoltTray\logi-volttray.log`（EXE 同目录 / %TEMP% 逐级兜底），记录各启动阶段里程碑与失败原因，超过 1MB 自动轮转。
- **失败弹窗**：单实例初始化、图标预渲染、托盘创建等关键步骤失败时，弹出中文错误提示并附日志路径，不再静默退出。
- **单实例可感知**：已有实例运行时再次双击，会弹出「LogiVoltTray 已在运行」并指引查看托盘位置，而不是毫无反应。
- **启动反馈**：每次成功启动发送静默通知「LogiVoltTray 正在运行」，说明托盘位置（通知失败仅记日志，不影响启动）。
- **panic 可见**：任何 panic 写入日志；GUI 线程 panic 额外弹窗提示。

> 诊断指引：若再遇启动异常，把日志文件（路径见上）发给开发者即可精确定位失败阶段。
